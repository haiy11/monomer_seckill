## 3. 验证一：异步下单（削峰）

1. 用 `user1` 登录拿到 JWT（或直接打开前端 `unified_gateway/index.html` 走网关）。
2. 对某个秒杀商品发起抢购 `POST /api/seckill/{seckillGoodsId}`。
3. 观察：**接口立刻返回订单号**（Redis 预扣 + 发消息即返回，不等 DB 写）。
4. 立即刷新「我的订单」列表，短暂延迟后订单出现——订单是消费者异步落库的。

验证削峰的关键点：接口响应里没有了「DB 扣库存 + 插订单」的同步耗时，请求线程只做了
「Redis Lua 预扣 + 发一条消息（发布确认）」。

## 4. 验证二：死信队列超时自动取消（15 分钟）

1. 抢购一单，**不支付**。
2. 观察 RabbitMQ 管理台：`seckill.order.delay.queue` 里滞留了 1 条超时消息（`expiration=900000`）。
3. 等 15 分钟（TTL 到期），消息从延迟队列消失、进入 `seckill.order.timeout.queue` 并被消费。
4. 观察结果：
   - 订单状态从「待支付」变为「超时关闭」（status=3）；
   - 库存自动回补：DB `seckill_goods.seckill_stock +1`，Redis `seckill:stock:{id} +1`，
     `seckill:users:{id}` 移除该用户。

**不想等 15 分钟？** 临时把 Nacos `seckill-service.yml` 的 `seckill.order-timeout-minutes` 改成 `1`，
重启 seckill-service 后重新抢购一单，1 分钟后即可观察自动关闭。

## 5. 验证三：消息可靠性（可选）

1. **发布确认**：抢购接口返回成功即代表消息已被 Broker 确认落盘（`publisher-confirm-type: correlated`）。
2. **消费幂等**：连续快速抢购同一商品，同一用户只产生一单（Redis Lua 判重 + 订单号/唯一索引双兜底）。
3. **JSON 消息**：在 RabbitMQ 管理台队列里 `Get messages`，能看到 JSON 格式的消息体，
   而非 Java 原生序列化的乱码。

## 6. 常见问题

| 现象 | 排查                                              |
|------|-------------------------------------------------|
| 启动报 RabbitMQ 连接失败 | 账号/端口/vhost 是否正确（`admin`/`admin123`，vhost `/`）  |
| 队列已存在但参数冲突 `PRECONDITION_FAILED` | 旧队列参数变了，需先删旧队列（或改队列名）再启动                        |
| 订单秒回但一直不落库 | 检查消费者是否就绪、`seckill.order.queue` 是否有积压、DB 是否报错   |
| 超时消息不触发 | 延迟队列 `x-dead-letter-routing-key` 是否等于超时队列绑定 key |
| 重复下单仍被拦截 | 符合预期：Redis 判重 + `uk_seckill_user` 唯一索引兜底        |

> 原理与面试知识点见 `knowledge/P8-消息队列知识.md`。
