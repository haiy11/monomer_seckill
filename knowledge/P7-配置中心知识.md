# P7 配置中心 + 动态刷新（Nacos Config）

> 阶段目标：把散落在各服务 `application.yml` 里的配置集中到 Nacos，实现「改配置不重启」，
> 并支持 dev/test/prod 多环境隔离。核心演示点：**修改 Sentinel 限流/熔断阈值不重启生效**。

---

## 一、为什么要配置中心

微服务拆得越细，配置越分散，痛点越明显：

| 痛点 | 没有配置中心 | 有配置中心 |
|------|------------|-----------|
| 配置分散 | 每个服务的 `application.yml` 各自维护，改一处要改多处 | 集中到一个平台，一处维护 |
| 改配置要重启 | 改限流阈值/开关必须重新打包部署 | 动态刷新，秒级生效 |
| 多环境难管 | dev/test/prod 靠人工复制 + 手动改 | dataId/profile/namespace 天然隔离 |
| 敏感信息外泄 | 数据库密码写死在代码仓库 | 集中管控 + 权限 + 加密 |

本项目的典型场景：秒杀大促时想把网关限流 QPS 从 100 调到 200，或把热点商品限流收紧，
**不应该重启服务**，而应该在 Nacos 控制台改一下配置即可。

---

## 二、Nacos Config 核心概念

| 概念 | 含义 | 本项目取值 |
|------|------|-----------|
| **dataId** | 一个配置文件的唯一标识（类似文件名） | `seckill-service.yml` 等 |
| **group** | 配置分组，用于隔离不同用途/团队 | `DEFAULT_GROUP` |
| **namespace** | 租户级隔离，用于隔离不同环境（dev/test/prod） | 未启用，用 `public` |
| **file-extension** | 配置文件格式 | `yml` |

三者共同定位一份配置：**namespace + group + dataId** 唯一确定一条配置。

dataId 约定（本项目采用 profile 后缀方式，不走 namespace）：
- 基础配置：`{服务名}.yml`（所有环境共享）
- 环境配置：`{服务名}-{profile}.yml`（如 `seckill-service-dev.yml` / `-prod.yml`）

---

## 三、接入方式（Spring Cloud Alibaba 2023.x）

Spring Boot 3 + Spring Cloud 2023 起，配置中心改用 **`spring.config.import`**（旧的
`bootstrap.yml` 需要额外引入 `spring-cloud-starter-bootstrap`，已不推荐）。

### 1. 依赖

```xml
<!-- 各业务服务 + 网关 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>

<!-- 公共模块（仅为了用 @RefreshScope 注解） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-context</artifactId>
</dependency>
```

版本由父 pom 里的 `spring-cloud-alibaba-dependencies` BOM 统一仲裁，无需写版本号。

### 2. application.yml

```yaml
spring:
  application:
    name: seckill-service
  config:
    import:
      - optional:nacos:seckill-common.yml          # 共享配置（jwt）
      - optional:nacos:seckill-service.yml         # 本服务基础配置
      - optional:nacos:seckill-service-${spring.profiles.active:dev}.yml  # 环境配置
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
      config:
        server-addr: localhost:8848
        file-extension: yml
        group: DEFAULT_GROUP
```

要点：
- `optional:` 前缀表示「配置不存在也不报错」，服务可降级用本地/默认值。
- `spring.config.import` 引入的多个 dataId，**后引入的优先级更高**（环境配置覆盖基础配置）。
- 本地 `application.yml` 只保留 `server.port`、`spring.application.name` 与 Nacos 连接信息，
  其余业务配置全部搬到 Nacos。

### 3. 多环境切换

```bash
# 默认 dev
mvn spring-boot:run
# 切 prod
mvn spring-boot:run -Dspring-boot.run.arguments=--spring.profiles.active=prod
# 或打包后
java -jar seckill-service.jar --spring.profiles.active=prod
```

`${spring.profiles.active:dev}` 会被替换成实际环境名，从而加载对应的 `-dev.yml` / `-prod.yml`。

## 四、动态刷新原理（@RefreshScope）

### 触发链路

```
Nacos 控制台改配置
   ↓ Nacos 服务端推送（长轮询 / gRPC）
NacosConfigManager 监听到变更
   ↓ 发布 RefreshEvent
ContextRefresher.refresh()
   ↓ ① 刷新 Environment（新增/更新 PropertySource）
   ↓ ② RefreshScope.refreshAll()：销毁并重建所有 @RefreshScope Bean
   ↓ 发布 RefreshScopeRefreshedEvent
业务监听该事件 → 重载规则（本项目重载 Sentinel 规则）
```

### @RefreshScope 的作用

普通 `@Component` 是单例，构造后字段值就固定了。`@RefreshScope` 会把它变成「作用域代理」：
- 每次注入的是代理对象，真正目标按需创建；
- 刷新时旧目标被销毁，下次访问重建一个，`@Value`/`@ConfigurationProperties` 重新解析，
  于是拿到新配置。

```java
@Data
@Component
@RefreshScope
@ConfigurationProperties(prefix = "sentinel.seckill")
public class SentinelProperties {
    private double degradeRtMs = 200;      // 默认值兜底
    private double slowRatioThreshold = 0.2;
    // ...
}
```

> `@Value` 和 `@ConfigurationProperties` 都能配合 `@RefreshScope` 刷新。
> 区别：`@ConfigurationProperties` 适合一组相关配置（类型安全 + 校验），`@Value` 适合零散一两个值。
> 两者都必须「通过 Spring 容器管理的 Bean」访问才可刷新，直接 `new` 或 static 读取不行。

### 只刷新还不够——需要「消费」新值

`@RefreshScope` 只能保证 Bean 里的值变了，**不会自动把已经加载到第三方组件里的旧值替换掉**。
Sentinel 规则就是一个典型例子：规则已通过 `DegradeRuleManager.loadRules()` 加载进 Sentinel
内存，光改配置 Bean 不重载规则，限流阈值不会变。

所以本项目的做法是监听 `RefreshScopeRefreshedEvent`，事件触发时**整体重载规则**：

```java
@EventListener(RefreshScopeRefreshedEvent.class)
public void onConfigRefresh(RefreshScopeRefreshedEvent event) {
    loadDegradeRules();
    loadParamFlowRules();
}
```

这就是「修改限流阈值不重启生效」的完整闭环。

## 六、多环境三选一

1. **profile 后缀 dataId（本项目）**：`{服务}-{profile}.yml`，最简单，适合服务数量不多。
2. **namespace 隔离**：为 dev/test/prod 各建一个 namespace（每个 namespace 有独立 ID），
   `spring.cloud.nacos.config.namespace` 指定。隔离最彻底，但需在控制台预建 namespace。
3. **group 隔离**：`DEFAULT_GROUP` / `DEV_GROUP` / `PROD_GROUP`，`spring.cloud.nacos.config.group` 指定。

面试话术：优先讲 namespace 隔离（生产标准做法），本项目为了演示方便用了 profile 后缀。

## 七、常见坑

1. **改了配置没生效**：
   - 确认 dataId/group 与 `spring.config.import` 完全一致；
   - 确认类/字段没有加 `@RefreshScope`；
   - 确认是「通过 Spring Bean」读取，而非 `new`/static 读取。
2. **`@ConfigurationProperties` 不刷新**：必须同时加 `@RefreshScope`（并且用 `@Component`
   注册，而不是 `@EnableConfigurationProperties`），否则刷新时不会重新绑定。
3. **`@Scheduled` 定时任务别套 `@RefreshScope`**：`@Scheduled` 方法靠后处理器在目标 Bean 创建时
   注册，作用域代理会破坏注册，容易失效。本项目的超时扫描间隔是「集中管理但需重启生效」。
4. **网关路由动态刷新**：`spring.cloud.gateway.routes` 放进 Nacos 后，改路由要触发
   `RefreshRoutesEvent` 才能让 `CachingRouteLocator` 重建，否则需重启。本项目未做路由动态刷新，
   只做配置集中管理。
5. **多级缓存 TTL 暂未动态化**：P6 的 Caffeine/Redis TTL 目前仍是 `SeckillConstants`/`GoodsOrderConstants`
   里的常量，不在 Nacos 里。要让 TTL 动态生效需在刷新时重建 Caffeine 缓存对象并更新 Redis 写 TTL，
   属于「刷新后重建资源」类问题，与 Sentinel 规则重载同理，可作为后续扩展练习。
6. **改了 jwt.secret 的副作用**：旧 token 立即全部失效（因为验签密钥变了）——这正是密钥轮换的
   预期行为，演示时要有心理预期。
7. **`spring.config.import` 顺序**：后导入的优先级更高，环境配置要放在基础配置之后。

## 八、验证动态刷新（实操）

1. 启动 Nacos + 发布配置（`publish-configs.ps1`）。
2. 启动服务，观察日志出现 `[Sentinel 网关] 已加载网关流控规则：seckill_api QPS=100`。
3. 在 Nacos 控制台把 `gateway-service.yml` 的 `sentinel.gateway.seckill-qps` 改成 `5` 并发布。
4. 观察日志出现 `检测到 Nacos 配置刷新，重载网关流控规则 ... QPS=5.0`，无需重启。
5. 用 JMeter/ab 以 >5 QPS 打 `/api/seckill/**`，即可看到 429 限流响应。

详见 `docs/P7-配置中心.md`。
