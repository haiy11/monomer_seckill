# P7 配置中心 + 动态刷新（Nacos Config）

> 阶段目标：把散落在各服务 `application.yml` 里的配置集中到 Nacos，实现「改配置不重启」，
> 并支持 dev/test/prod 多环境隔离。核心演示点：**修改 Sentinel 限流/熔断阈值不重启生效**。
>
> 本文按「配置的一生」组织：**发布 → 拉取 → 推送 → 刷新生效**，四个环节串起完整链路。

---

## 一、为什么要配置中心

微服务拆得越细，配置越分散，痛点越明显：

| 痛点 | 没有配置中心 | 有配置中心 |
|------|------------|-----------|
| 配置分散 | 每个服务的 `application.yml` 各自维护，改一处要改多处 | 集中到一个平台，一处维护 |
| 改配置要重启 | 改限流阈值/开关必须重新打包部署 | 动态刷新，秒级生效 |
| 多环境难管 | dev/test/prod 靠人工复制 + 手动改 | dataId/profile/namespace 天然隔离 |
| 敏感信息外泄 | 数据库密码写死在代码仓库 | 集中管控 + 权限 + 加密 |

本项目的典型场景：秒杀大促时想把网关限流 QPS 从 100 调到 200，或把热点商品限流收紧，
**不应该重启服务**，而应该在 Nacos 控制台改一下配置即可。

---

## 二、Nacos Config 核心概念

| 概念 | 含义 | 本项目取值 |
|------|------|-----------|
| **dataId** | 一个配置文件的唯一标识（类似文件名） | `seckill-service.yml` 等 |
| **group** | 配置分组，用于隔离不同用途/团队 | `DEFAULT_GROUP` |
| **namespace** | 租户级隔离，用于隔离不同环境（dev/test/prod） | 未启用，用 `public` |
| **file-extension** | 配置文件格式 | `yml` |

**namespace + group + dataId** 三者唯一确定一份配置。

dataId 约定（本项目采用 profile 后缀方式，不走 namespace）：
- 基础配置：`{服务名}.yml`（所有环境共享）
- 环境配置：`{服务名}-{profile}.yml`（如 `seckill-service-dev.yml` / `-prod.yml`）

> 记忆点：**dataId 是「拉取」和「推送」的最小单位**——服务按 dataId 订阅，Nacos 也按 dataId
> 推送变更，后面「四、配置的一生」会反复用到这个概念。

## 三、接入方式：依赖分工 + 本地配置

Spring Boot 3 + Spring Cloud 2023 起，配置中心改用 **`spring.config.import`**（旧的
`bootstrap.yml` 需要额外引入 `spring-cloud-starter-bootstrap`，已不推荐）。

### 3.1 两个依赖的精确分工与包含关系

```xml
<!-- 4 个业务服务 + 网关 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>

<!-- 只加到 common-service（公共库） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-context</artifactId>
</dependency>
```

| 依赖 | 加到哪 | 职责 |
|------|--------|------|
| `spring-cloud-starter-alibaba-nacos-config` | 4 个服务 + 网关 | **拉配置 + 监听变化**：提供 `NacosConfigDataLoader`，处理 `spring.config.import: nacos:...`，启动时连 Nacos 拉 dataId，并注册监听器持续监听变更 |
| `spring-cloud-context` | 只加 `common-service` | **刷新机制**：提供 `@RefreshScope` 注解、`RefreshScope` 作用域、`ContextRefresher`，配置变更后能重建 `@RefreshScope` Bean |

**包含关系**：`nacos-config` 内部本就传递依赖了 `spring-cloud-context`，所以 4 个服务和网关
**不用再单独加** `spring-cloud-context`。`common-service` 是公共库、自己不连 Nacos，但里面的
`TokenService` 需要 `@RefreshScope` 注解才能编译，所以才单独加 `spring-cloud-context`。

一句话：**`nacos-config` = 拉配置 + 监听；`spring-cloud-context` = 配置变了之后让 `@RefreshScope` 生效。**

版本由父 pom 里的 `spring-cloud-alibaba-dependencies` BOM 统一仲裁，无需写版本号。

### 3.2 本地 application.yml 保留什么

本地 `application.yml` 只保留 4 类信息（以 seckill-service 为例）：

```yaml
server:
  port: 7003                        # ① 本地端口（部署属性，留在本地）

spring:
  application:
    name: seckill-service           # ② 服务名（注册 + dataId 前缀）
  config:
    import:                         # ③ 要拉取的 dataId 清单
      - optional:nacos:seckill-common.yml
      - optional:nacos:seckill-service.yml
      - optional:nacos:seckill-service-${spring.profiles.active:dev}.yml
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848  # ④ 注册中心地址
      config:
        server-addr: localhost:8848  # ④ 配置中心地址
        file-extension: yml
        group: DEFAULT_GROUP
```

**数据源、Redis、MyBatis、`jwt.secret`、`sentinel.*` 阈值、网关路由等业务配置，本地一概没有**，
全部在 Nacos 里。

要点：
- `optional:` 前缀表示「这个 dataId 不存在时不报错」，用默认值/继续启动。
- `spring.config.import` 引入多个 dataId 时，**后引入的优先级更高**（环境配置覆盖基础配置）。

## 四、配置的一生：发布 → 拉取 → 推送 → 刷新生效

### 4.1 发布：publish-configs.ps1 做了什么

执行 `docs/P7-nacos-config/publish-configs.ps1`，脚本遍历该目录下 13 个 yml 文件，对每个文件：

- `dataId` = 文件名（如 `seckill-service.yml`）
- `group` = `DEFAULT_GROUP`
- 通过 Nacos Open API `POST /nacos/v1/cs/configs` 发布内容

发布后可在 `http://localhost:8848/nacos` 控制台「配置管理 → 配置列表」看到这 13 条配置。

> 也可以不跑脚本，在控制台手动新建配置：dataId 与文件名同名、group 用 `DEFAULT_GROUP`、
> 格式选 YAML，粘贴文件内容即可。

### 4.2 拉取：启动时发生了什么

关键点：**配置拉取发生在 ConfigData 阶段，早于任何 Bean 的创建**。

```
应用启动
  → Spring Boot 读本地 application.yml
  → 看到 spring.config.import，交给 NacosConfigDataLoader（来自 nacos-config 依赖）
  → 按 config.server-addr 连 Nacos，逐条拉取 dataId
  → 把 Nacos 配置合并进 Environment（与本地 server.port 并存）
  → 才开始创建 Bean：数据源、Redis、MyBatis、JWT、Sentinel 阈值、网关路由……
     这些值此时都已经从 Nacos 拿到了
```

所以「本地没有数据源配置」不会报错——因为 Bean 创建前数据源配置已经通过 Nacos 进了 Environment。

> 注意：`optional:` 容的是「dataId 不存在」，**不是**「Nacos 服务没启动」。Nacos 连不上属于
> 连接失败，服务启动会报错。正确顺序：先起 Nacos → 再发布配置 → 最后起服务。

### 4.3 推送：订阅模型（只推给订阅者）

Nacos 的推送是 **订阅模型（publish/subscribe）**，不是广播给所有连上 Nacos 的服务。

**订阅关系怎么建立**：每个服务在启动拉取某个 dataId 时，SCA 框架顺手给这个 dataId 注册一个
监听器（`ConfigService.addListener(dataId, group, listener)`），相当于对服务器说「我对
`seckill-service.yml` 感兴趣」。服务器维护一张映射表：

```
(dataId, group, namespace)  →  订阅了它的客户端连接列表
```

**发布变更时只推给订阅者**：控制台改了 `gateway-service.yml` 并发布，服务器查「谁订阅了
`gateway-service.yml`」，只给这些客户端连接推变更通知。

| 你改的配置 | 谁会被推送到 | 原因 |
|-----------|-------------|------|
| `seckill-common.yml`（`jwt.secret`） | **全部 4 个服务 + 网关** | 都 import 了这个共享配置，都订阅了它 |
| `seckill-service.yml`（`sentinel.seckill.*`） | **只有 seckill-service** | 只有它 import 了这个 dataId |
| `gateway-service.yml`（`sentinel.gateway.seckill-qps`） | **只有 gateway-service** | 只有网关 import 了它 |

**粒度澄清（易混点）**：推送粒度是 **dataId**，不是 key（配置项），也不是「服务自己判断用没用到
这个 key」。只要 `seckill-service.yml` 里任意一个 key 变了，订阅了它的 seckill-service 就会收到
推送，然后**整个服务**刷新：

```
收到 dataId 变更 → SCA 刷新该服务整个 Environment（更新该 dataId 的 PropertySource）
  → RefreshScope 重建所有 @RefreshScope Bean（不管具体哪个 key 变了）
  → 发布 RefreshScopeRefreshedEvent
  → 我们的 SentinelConfig 监听事件 → 无条件整体重载规则
```

即：**「按 dataId 订阅 + 推送」是精确的，但「推送之后的处理」按整个服务来**。我们的代码收到任何
刷新事件都会重载一次 Sentinel 规则（规则重载幂等，简单最不易错）。

**传输层**：Nacos 2.x 用 **gRPC 双向流**把变更推下来（非轮询）；Nacos 1.x 靠**长轮询**模拟推送。
本项目配 Nacos 2.x，所以控制台一发布、几秒内服务就能收到。

### 4.4 刷新生效：@RefreshScope + 重载规则

收到推送只是第一步，把新配置「用起来」靠下面这条链路：

```
Nacos 服务器向订阅者推送变更（gRPC）
   ↓ NacosConfigManager 的监听器收到
   ↓ 发布 RefreshEvent
ContextRefresher.refresh()
   ↓ ① 刷新 Environment（更新该 dataId 对应的 PropertySource）
   ↓ ② RefreshScope.refreshAll()：销毁并重建所有 @RefreshScope Bean
   ↓ 发布 RefreshScopeRefreshedEvent
业务监听该事件 → 重载规则（本项目重载 Sentinel 规则）
```

**@RefreshScope 的作用**：普通 `@Component` 是单例，构造后字段值就固定了。`@RefreshScope` 会把它
变成「作用域代理」：

- 每次注入的是代理对象，真正目标按需创建；
- 刷新时旧目标被销毁，下次访问重建一个，`@Value`/`@ConfigurationProperties` 重新解析，
  于是拿到新配置。

```java
@Data
@Component
@RefreshScope
@ConfigurationProperties(prefix = "sentinel.seckill")
public class SentinelProperties {
    private double degradeRtMs = 200;      // 默认值兜底
    private double slowRatioThreshold = 0.2;
    // ...
}
```

> `@Value` 和 `@ConfigurationProperties` 都能配合 `@RefreshScope` 刷新。
> 区别：`@ConfigurationProperties` 适合一组相关配置（类型安全 + 校验），`@Value` 适合零散一两个值。
> 两者都必须「通过 Spring 容器管理的 Bean」访问才可刷新，直接 `new` 或 static 读取不行。

**只刷新还不够——需要「消费」新值**：`@RefreshScope` 只能保证 Bean 里的值变了，**不会自动把已经
加载到第三方组件里的旧值替换掉**。Sentinel 规则就是典型：规则已通过 `DegradeRuleManager.loadRules()`
加载进 Sentinel 内存，光改配置 Bean 不重载规则，限流阈值不会变。

所以本项目的做法是监听 `RefreshScopeRefreshedEvent`，事件触发时**整体重载规则**：

```java
@EventListener(RefreshScopeRefreshedEvent.class)
public void onConfigRefresh(RefreshScopeRefreshedEvent event) {
    loadDegradeRules();
    loadParamFlowRules();
}
```

这就是「修改限流阈值不重启生效」的完整闭环。

## 五、多环境：profile 后缀 + 三选一

### 5.1 切换方式

```bash
# 默认 dev
mvn spring-boot:run
# 切 prod
mvn spring-boot:run -Dspring-boot.run.arguments=--spring.profiles.active=prod
# 或打包后
java -jar seckill-service.jar --spring.profiles.active=prod
```

`${spring.profiles.active:dev}` 会被替换成实际环境名，从而加载对应的 `-dev.yml` / `-prod.yml`。

### 5.2 三种隔离方案

1. **profile 后缀 dataId（本项目）**：`{服务}-{profile}.yml`，最简单，适合服务数量不多。
2. **namespace 隔离**：为 dev/test/prod 各建一个 namespace（每个 namespace 有独立 ID），
   `spring.cloud.nacos.config.namespace` 指定。隔离最彻底，但需在控制台预建 namespace。
3. **group 隔离**：`DEFAULT_GROUP` / `DEV_GROUP` / `PROD_GROUP`，`spring.cloud.nacos.config.group` 指定。

面试话术：优先讲 namespace 隔离（生产标准做法），本项目为了演示方便用了 profile 后缀。

## 七、常见坑

1. **改了配置没生效**：
   - 确认 dataId/group 与 `spring.config.import` 完全一致；
   - 确认类/字段没有加 `@RefreshScope`；
   - 确认是「通过 Spring Bean」读取，而非 `new`/static 读取。
2. **`@ConfigurationProperties` 不刷新**：必须同时加 `@RefreshScope`（并且用 `@Component`
   注册，而不是 `@EnableConfigurationProperties`），否则刷新时不会重新绑定。
3. **`@Scheduled` 定时任务别套 `@RefreshScope`**：`@Scheduled` 方法靠后处理器在目标 Bean 创建时
   注册，作用域代理会破坏注册，容易失效。本项目的超时扫描间隔是「集中管理但需重启生效」。
4. **网关路由动态刷新**：`spring.cloud.gateway.routes` 放进 Nacos 后，改路由要触发
   `RefreshRoutesEvent` 才能让 `CachingRouteLocator` 重建，否则需重启。本项目未做路由动态刷新，
   只做配置集中管理。
5. **多级缓存 TTL 暂未动态化**：P6 的 Caffeine/Redis TTL 目前仍是 `SeckillConstants`/`GoodsOrderConstants`
   里的常量，不在 Nacos 里。要让 TTL 动态生效需在刷新时重建 Caffeine 缓存对象并更新 Redis 写 TTL，
   属于「刷新后重建资源」类问题，与 Sentinel 规则重载同理，可作为后续扩展练习。
6. **改了 jwt.secret 的副作用**：旧 token 立即全部失效（因为验签密钥变了）——这正是密钥轮换的
   预期行为，演示时要有心理预期。
7. **`spring.config.import` 顺序**：后导入的优先级更高，环境配置要放在基础配置之后。
8. **`optional:` 不等于「Nacos 挂了也能起」**：它只容「dataId 不存在」，Nacos 连不上是连接失败，
   启动仍会报错。

## 八、验证动态刷新（实操）

1. 启动 Nacos + 发布配置（`publish-configs.ps1`）。
2. 启动服务，观察日志出现 `[Sentinel 网关] 已加载网关流控规则：seckill_api QPS=100`。
3. 在 Nacos 控制台把 `gateway-service.yml` 的 `sentinel.gateway.seckill-qps` 改成 `5` 并发布。
4. 观察日志出现 `检测到 Nacos 配置刷新，重载网关流控规则 ... QPS=5.0`，无需重启。
5. 用 JMeter/ab 以 >5 QPS 打 `/api/seckill/**`，即可看到 429 限流响应。

详见 `docs/P7-配置中心.md`。
