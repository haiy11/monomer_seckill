# P5 高可用限流熔断知识

> 本文件整理秒杀项目 P5 阶段「高可用限流熔断：Sentinel 限流、降级、热点参数规则」涉及的通用知识点，作为学习笔记与面试复习材料。
> 代码工程对应 `monomer_seckill_backend/monomer_seckill_backend_cloud/`，改动集中在 `gateway-service` 与 `seckill-service`。
>
> 本文按「从入门疑问到深入原理」的顺序组织：先讲引入的依赖各自干什么 → 再讲为什么网关和秒杀服务两边都要装 → 最后讲两个配置类各自是怎么起作用的。

## 1. P5 阶段做了什么（概览）

P5 的目标是**给系统加一层「高可用」保护**：P4 之后流量都从网关进来，但再大的流量进来也只会硬扛，一旦某个服务变慢/被热点打爆，会拖垮整个链路。P5 引入 Sentinel，在两条防线上做防护：

| 防线 | 谁做 | 方式 |
|------|------|------|
| 网关限流 | gateway-service | 秒杀下单接口 QPS=100，超出的请求在网关就被拦下（HTTP 429） |
| 服务熔断 + 热点限流 | seckill-service | 慢调用比例熔断（>20% 触发）+ 按商品 ID 的热点参数限流 |

新增/改动的文件：

```
gateway-service/
├── pom.xml                                    # + spring-cloud-alibaba-sentinel-gateway、sentinel-transport-simple-http
├── src/main/resources/application.yml         # + spring.cloud.sentinel.transport（Dashboard，可选）
└── src/main/java/com/example/seckill/gateway/
    └── sentinel/GatewaySentinelConfig.java    # 限流响应 + 网关流控规则（QPS=100）

seckill-service/
├── pom.xml                                    # + spring-cloud-starter-alibaba-sentinel
├── src/main/resources/application.yml         # + spring.cloud.sentinel.eager/transport
└── src/main/java/com/example/seckill/seckill/
    ├── config/SentinelConfig.java             # 熔断规则 + 热点参数限流规则
    ├── controller/SentinelDemoController.java # 熔断演示端点（/api/seckill/demo/slow）
    └── service/SeckillService.java            # + @SentinelResource + blockHandler
```

## 2. 引入的依赖各自起什么作用？

> 学习疑问：网关引入了两个依赖，秒杀服务引入了一个依赖，它们分别干什么？为什么两边引的不一样？

### 2.1 先建立心智模型：Sentinel 到底跑在哪？

容易误以为 Sentinel 像 MySQL/Redis 一样是个「独立服务」，要用的时候连一下。**不是的**。Sentinel 的核心是**一个 jar 库，嵌在你自己的服务进程里**，相当于给每个服务请了一个「门口的流量管理员」：

```
请求 → [你服务的 Controller]
          ↑
     Sentinel 这个"管理员"挡在门口：数 QPS、看响应时间、超了就拦/熔断
```

它不像 Nacos 那样要单独启动一个进程（Nacos 是独立注册中心，Sentinel 核心是库）。所谓「Sentinel Dashboard」是另一个**可选**的可视化控制台，跟限流逻辑本身无关——不启动它，限流照样生效。

所以「引入 Sentinel」本质上就是：**往你的服务里塞一个 jar，并告诉它「在哪些接口上、按什么规则拦人」。**

一个 Spring Boot **starter** 的本质，你在单体里其实见过：`spring-boot-starter-web` 不是「一个」jar，而是帮你把 Tomcat、Spring MVC、Jackson 等一堆 jar 一次性拉进来 + 自动配置好。

### 2.2 三个依赖

| 依赖 | 装到哪 | 一句话作用 |
|---|---|---|
| `spring-cloud-starter-alibaba-sentinel` | 普通 MVC 服务（seckill-service） | **全套安装包**：引擎 + Servlet 适配器 + `@SentinelResource` 切面 + 热点限流 + Dashboard 上报 |
| `spring-cloud-alibaba-sentinel-gateway` | 响应式网关（gateway-service） | **转接头**：让引擎适配 Spring Cloud Gateway（`SentinelGatewayFilter` + `GatewayFlowRule`） |
| `sentinel-transport-simple-http` | 想连 Dashboard 的服务 | **上报/接收通道**，仅用于可视化，可选 |

逐个展开：

**① `spring-cloud-starter-alibaba-sentinel`（秒杀服务用）**——给「普通 Spring Boot（Servlet/MVC）服务」用的标准入门包，自动带进来并装配好：

| 它自动带进来的东西 | 作用 |
|---|---|
| `sentinel-core` | Sentinel 的**规则引擎本体**（数 QPS、开熔断器） |
| `sentinel-spring-webmvc-v6x-adapter` | **Servlet 适配器**：自动注册拦截器，把 `/api/**` URL 都纳入监控（`v6x` 对应 Spring MVC 6.x / Spring Boot 3） |
| `sentinel-annotation-aspectj` | 让 `@SentinelResource` 注解生效（AOP 切面） |
| `sentinel-parameter-flow-control` | 热点参数限流 `ParamFlowRule` 的能力 |
| `sentinel-transport-simple-http` | Dashboard 上报（标准 starter 已自带） |

**② `spring-cloud-alibaba-sentinel-gateway`（网关用）**——给 Spring Cloud Gateway（响应式/WebFlux）用的专门适配包。因为网关是响应式技术栈，**不能**用标准 starter（标准 starter 带的是 Servlet 适配器，网关里没有 Servlet，硬塞会冲突，与 P4 笔记「网关不可引入 `spring-boot-starter-web`」是同一道理）：

| 带进来的东西 | 作用 |
|---|---|
| `sentinel-spring-cloud-gateway-adapter` | **网关适配器**：提供 `SentinelGatewayFilter`（一个 GlobalFilter），请求经过网关时先被它包一层 |
| `sentinel-api-gateway-adapter-common` | 网关专用规则类型：`GatewayFlowRule`、`ApiDefinition`（按路径分组）等 |

**③ `sentinel-transport-simple-http`（网关额外加）**——「服务 ↔ Dashboard」的通信通道，负责：服务 → Dashboard 定时上报心跳/监控数据；Dashboard → 服务 推送动态规则。对应 `application.yml` 里的 `transport.dashboard`（上报地址）与 `transport.port`（本服务开的端口）。

> **关键理解：它是可选的。** 没有它、不启动 Dashboard，限流熔断照样生效（规则是代码里 `loadRules` 写死的）。它只影响「可视化看监控」和「控制台动态改规则」。网关要额外手动加这一条，是因为网关专用包不像标准 starter 那样自动带上它。

### 2.3 顺带：两个 groupId 的区别

- `com.alibaba.csp`：Sentinel **自己的核心库**（独立于 Spring，谁都能用）；
- `com.alibaba.cloud`：**Spring Cloud Alibaba 项目**，职责是「把 Sentinel/Nacos 这些阿里组件桥接进 Spring Boot/Spring Cloud 的自动配置体系」。

所以 `com.alibaba.cloud` 的 starter 本质是「桥 + 自动配置」，真正干活的引擎还是 `com.alibaba.csp` 的 Sentinel。

## 3. 三个容易混的概念：限流 / 熔断 / 降级

这是面试必考，先分清「是什么」：

| 概念 | 触发原因 | 动作 | 目的 |
|------|----------|------|------|
| **限流（Flow Control）** | 请求量超过阈值（如 QPS>100） | 拒绝多余请求 | 保护系统不被流量冲垮 |
| **熔断（Circuit Breaker）** | 依赖/服务出现大量失败或变慢 | 打开断路器，快速失败，不再调用 | 防止故障扩散、雪崩 |
| **降级（Fallback）** | 熔断/限流/异常发生时 | 返回兜底结果（如「系统繁忙」） | 给用户一个可接受的响应而非报错 |

一句话记忆：**限流是「量太大，拒一部分」，熔断是「它坏了，先别调」，降级是「出事了，给兜底」**。三者经常配合：熔断触发后，对被熔断的调用走「降级」逻辑。

Sentinel 里这三者的落地物：

- 限流 → `FlowRule` / 网关 `GatewayFlowRule` / 热点 `ParamFlowRule`
- 熔断 → `DegradeRule`（异常比例、异常数、**慢调用比例**三种）
- 降级 → `@SentinelResource` 的 `fallback` / `blockHandler`

## 4. 限流与熔断防的是不同的「故障」——为什么网关和秒杀服务都要装？

> 学习疑问：为什么要在网关和秒杀服务都装 Sentinel？只装在网关可以吗？「网关限流是全局限流、秒杀是单接口限流」这样理解对吗？

### 4.1 先纠正：网关限流不是「全局限流」

「网关限流是把所有流量加起来超阈值才拦」——**不对**。网关限流也是**按资源分别计数**的，只是「资源」的定义是**路径/路由**，不是方法。本项目配的规则只对秒杀下单这一个路径：

```java
new ApiPathPredicateItem().setPattern("/api/seckill/**")  // 只匹配这个路径
...
new GatewayFlowRule("seckill_api")...setCount(100)         // 只有这个 API 分组 QPS=100
```

所以 `/api/seckill/**` 每秒超过 100 个才被拦，`/api/goods`、`/api/user/login` 等**完全不受影响**。网关限流也能「精确到某个路径」。

### 4.2 核心：它们防的是三件不同的事

| 能力 | 防的是什么故障 | 谁来感知 | 放哪最合适 |
|---|---|---|---|
| 网关限流（QPS） | **流量太大**（入口洪峰） | 网关在流量刚进来时就能数 | 网关（第一道门） |
| 服务熔断 | **依赖变慢/坏了**（Redis、DB 变慢） | 只有调用 Redis/DB 的那个服务自己能计时感知 | 服务内部（第二道保险） |
| 热点参数限流 | **某个商品被集中打爆** | 要看到「商品ID」这个业务参数 | 服务内部（方法参数） |

### 4.3 为什么「只装网关」不行？——两个场景

**场景 1：Redis 突然变慢（熔断的价值）**

- **只装网关**：网关看到流量没超 100 QPS，照常转发。但秒杀服务内部每个请求都卡在 Redis 上 3 秒，线程池很快被占满，服务假死。**网关完全看不出异常**（它只看到「流量不大」，看不到「Redis 慢了」）。
- **装了服务熔断**：秒杀服务自己给 Redis 调用计时，发现「超过 200ms 的调用占比 > 20%」，主动打开熔断器，后续请求**直接快速失败返回「系统繁忙」**，不再傻乎乎地调 Redis，保住自己不崩。

> 关键洞察：**熔断器必须放在「调用慢依赖的那一方」内部**，因为只有它自己能计时、知道依赖慢不慢。网关站在门口，看不到 Redis。

**场景 2：双 11 爆款商品（热点限流的价值）**

某商品 id=1 突然爆火，90% 的秒杀请求都打它。**只装网关**：总流量没超 100 QPS，网关不拦，但商品 1 的库存/Redis 被集中打爆，其它商品跟着遭殃。**装了热点限流**：秒杀服务按「商品ID」单独计数，商品 1 超 5 QPS 就拦（返回「该商品太火爆」），其它商品不受影响。网关在 HTTP 层，这种「按业务参数精细限流」放服务内部更自然。

### 4.4 三道防线，各管各的

```
外部流量
   │
   ▼
网关  ── 第一道：流量太大？超 100 QPS 就拦（省得下游白挨打）
   │（放行）
   ▼
秒杀服务  ── 第二道：Redis/DB 变慢？慢调用 >20% 就熔断（保护自己不崩）
        ── 第三道：某个商品被集中打？热点商品单独限流（保护其它商品）
```

三道防线挡三种不同的故障，**互相替代不了**：网关限流挡不住「流量不大但依赖变慢」；服务熔断挡不住「流量洪峰」（等打到服务内部才拦已晚）；热点限流需要业务参数，网关层不方便做。

一句话记：**网关管「进来多少」，服务管「自己坏没坏」。**

## 5. 为什么选 Sentinel 而不是 Hystrix（面试高频）

Hystrix 已进入维护模式、不再更新，Sentinel 是当前主流选择。关键对比：

| 维度 | Hystrix | Sentinel |
|------|---------|----------|
| 隔离策略 | 线程池/信号量隔离（重量级） | 信号量隔离（轻量）+ 并发线程数限流 |
| 熔断策略 | 异常比例（基于滑动窗口） | 异常比例 / 异常数 / **慢调用比例** 三种，更细 |
| 限流维度 | 无（只有熔断） | QPS、并发线程、**热点参数**、集群限流等 |
| 控制台 | Turbine + Dashboard（弱） | 官方 Dashboard（强，实时监控 + 动态规则） |
| 规则来源 | 代码/配置 | 代码 / Dashboard / Nacos 等动态数据源 |
| 活跃度 | 停止维护 | 阿里持续维护，Spring Cloud Alibaba 官方集成 |

本项目 P5 正是用了 Hystrix 没有的「慢调用比例熔断」和「热点参数限流」——这是选 Sentinel 的直观理由。

## 6. 网关限流是怎么生效的——三个管理类与「规则仓库」心智模型

> 学习疑问：`GatewaySentinelConfig` 这个类是怎么起到限流作用的？是不是定义了那几个 static 类，Sentinel 就自动限流了？

### 6.1 先纠正：这个类自己不「拦」请求

`GatewaySentinelConfig` 全程**没有拦任何一个请求**，它只做两件「配置」的事：告诉 Sentinel「被限流时返回什么」（`initBlockHandler`）、「限流规则是什么」（`loadGatewayRules`）。

**真正在请求路径上「拦人」的是 `SentinelGatewayFilter`**——一个 Spring Cloud Gateway 的全局过滤器，而且**它不是手写的**，是引入 `spring-cloud-alibaba-sentinel-gateway` 后由 SCA 自动装配注册的。启动日志里有这一行：

```
[Sentinel SpringCloudGateway] register SentinelGatewayFilter with order: -2147483648
```

所以完整分工是：

| 角色 | 谁干的 | 干什么 |
|---|---|---|
| **警察**（拦请求） | `SentinelGatewayFilter` | 依赖自动注册，每个请求经过网关时先过它 |
| **规则**（拦多少） | 手写的 `loadGatewayRules()` | 喂给 Sentinel 的规则仓库 |
| **被拦后返回什么** | 手写的 `initBlockHandler()` | 自定义成 429 + JSON |

### 6.2 三个 static 类是 Sentinel 库自带的「规则仓库」

`GatewayCallbackManager`、`GatewayApiDefinitionManager`、`GatewayRuleManager` **都不是手写定义的，而是 Sentinel 库自带的管理类**，它们是**进程内全局单例的「规则仓库」**。手写代码只是调它们的静态方法往里塞数据：

| 管理类 | 仓库里存什么 | 手写代码调用的方法 |
|---|---|---|
| `GatewayApiDefinitionManager` | 哪些路径算一组 | `loadApiDefinitions(...)` |
| `GatewayRuleManager` | 这组限多少 QPS | `loadRules(...)` |
| `GatewayCallbackManager` | 被拦时返回什么 | `setBlockHandler(...)` |

设完之后，数据躺在这些全局静态仓库里。`SentinelGatewayFilter` 在**每次请求时**去读 `GatewayRuleManager` 里的规则、数 QPS、超了就调 `GatewayCallbackManager` 里的 handler 返回 429。

> 至于 `setBlockHandler((exchange, t) -> {...})` 里的 lambda，才是当场写的一个「匿名处理函数」，作用就是「被拦时拼一个 429 JSON 返回」。它和 `GatewayCallbackManager` 是两回事：前者是传进去的「处理逻辑」，后者是存放它的「仓库」。

### 6.3 完整链路（启动时 + 请求时）

```
【启动时】手写的 run() 执行一次：
  GatewayApiDefinitionManager  ← 塞入「/api/seckill/** 归为 seckill_api 组」
  GatewayRuleManager           ← 塞入「seckill_api 组 QPS=100」
  GatewayCallbackManager       ← 塞入「被拦时返回 429 JSON」

【每个请求到达网关时】SentinelGatewayFilter（自动注册的那个警察）：
  ① 匹配请求路径 → 属于 seckill_api 组吗？
  ② 读 GatewayRuleManager 的规则，数这一秒已经放行多少个
  ③ 没超 → 放行；超了 → 调 GatewayCallbackManager 里的 handler 返回 429
```

> 一句话：**是「依赖带来的警察」+「手写喂进去的规则」两者配合**，才实现了限流。手写的这个类只负责喂规则，真正动手拦人的是自动注册的过滤器。

### 6.4 网关流控规则的两个「资源」维度

`GatewayFlowRule` 有两个维度：

| resourceMode | 含义 | 什么时候用 |
|--------------|------|-----------|
| `RESOURCE_MODE_ROUTE_ID` | 按路由 ID（如 `seckill-service`） | 对整条路由限流 |
| `RESOURCE_MODE_CUSTOM_API_NAME` | 按自定义 API 分组 | 对路由下的部分路径精确限流 |

本项目用**自定义 API 分组**，是因为 `seckill-service` 路由同时承载 `/api/seckill/**`（秒杀下单）和 `/api/seckill-goods/**`（商品浏览），只想限流前者：

```java
// 1. 定义 API 分组：路径前缀匹配 /api/seckill/**
Set<ApiPredicateItem> items = new HashSet<>();
items.add(new ApiPathPredicateItem()
        .setPattern("/api/seckill/**")
        .setMatchStrategy(SentinelGatewayConstants.URL_MATCH_STRATEGY_PREFIX));
ApiDefinition api = new ApiDefinition("seckill_api").setPredicateItems(items);
GatewayApiDefinitionManager.loadApiDefinitions(Set.of(api));

// 2. 流控规则：该 API 每秒最多 100 个请求
GatewayFlowRule rule = new GatewayFlowRule("seckill_api")
    .setResourceMode(SentinelGatewayConstants.RESOURCE_MODE_CUSTOM_API_NAME)
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(100)
    .setIntervalSec(1);
GatewayRuleManager.loadRules(Set.of(rule));
```

> ⚠️ 顺序细节：`SentinelGatewayFilter` 默认 `getOrder()` 返回 `Integer.MIN_VALUE`（最高优先级），**先于**我们 `-100` 的 `AuthGlobalFilter` 执行。所以超限时，连未登录的请求也会先拿到 429 而不是 401。这是 Sentinel 的默认取舍——限流放在鉴权之前，避免海量请求先把鉴权步骤打垮。

## 7. 为什么网关用 ApplicationRunner、秒杀服务用配置类？

> 学习疑问：`GatewaySentinelConfig` 实现了 `ApplicationRunner`，为什么不用配置类（`@PostConstruct`）？秒杀服务的 `SentinelConfig` 不就用配置类吗？是网关不能用配置类吗？

### 7.1 关键区别：两种「被拦后返回什么」的机制不一样

同样是「被拦后返回什么」，两边用的是**两套完全不同的机制**：

| | 网关 | 秒杀服务 |
|---|---|---|
| 被拦后返回什么 | **一个全局单例回调** `GatewayCallbackManager.setBlockHandler(...)` | **注解里写死的方法** `@SentinelResource(blockHandler = "seckillBlockHandler")` |
| 它的性质 | 全局只有一份，谁最后设谁生效 | 跟着每个方法走，各用各的 |
| 有「默认值」要覆盖吗 | **有**（SCA 会先设一个默认返回体） | **没有** |

### 7.2 网关为什么用 ApplicationRunner：为了「覆盖」默认值

SCA 的 `SentinelSCGAutoConfiguration` **自己也有一个 `@PostConstruct`**，启动时会往 `GatewayCallbackManager` 里设一个**默认的限流返回体**。手写代码要把它换成 429 JSON，就必须保证「手写的跑得比 SCA 的晚」。

问题在于：如果手写代码也用 `@PostConstruct`，两个 `@PostConstruct` **谁先谁后是不确定的**（不同 `@Configuration` 类的初始化顺序不保证）。万一 SCA 的默认设置跑在后面，手写的 429 就被覆盖了。

而 `ApplicationRunner.run()` 是在**整个 Spring 容器刷新完成之后**才执行，**一定晚于所有 `@PostConstruct`**。所以手写的 `setBlockHandler` 一定最后执行、一定覆盖默认值。

### 7.3 秒杀服务为什么能用配置类：只「新增」没「覆盖」

秒杀服务 `SentinelConfig` 里的两个方法：

```java
DegradeRuleManager.loadRules(rules);      // 往「熔断规则仓库」加规则
ParamFlowRuleManager.loadRules(rule);     // 往「热点规则仓库」加规则
```

本质是**「往一个 SCA 不会预置任何东西的空仓库里塞数据」**：SCA 不会在启动时预置任何 `DegradeRule`、`ParamFlowRule`，手写代码是「第一个也是唯一一个」写规则的人，不存在「被 SCA 默认规则覆盖」的竞争。

而秒杀服务的「被拦后返回什么」也不是全局回调，而是直接写在注解上（`@SentinelResource(blockHandler = "seckillBlockHandler")`），指向同类的兜底方法。**它不存在「谁最后设谁生效」的竞争**——注解本身就是唯一的、明确的声明，SCA 不会往注解里塞默认值。

### 7.4 一个原则

| 场景 | 有没有「要覆盖别人已设的值」 | 需要的机制 |
|---|---|---|
| 网关：自定义限流返回体 | 有（SCA 已设默认返回体） | `ApplicationRunner` 保证最后写 |
| 秒杀服务：加载熔断/热点规则 | 无（空仓库，我是唯一写入者） | `@PostConstruct` 配置类即可 |

> 补充：秒杀服务其实也有「URL 级」的默认拦截器（`SentinelWebInterceptor`）和对应的默认返回处理器，但本项目**没有在 URL 上配规则**，规则都配在 `@SentinelResource` 的资源 `seckill` 上，所以那个 URL 级默认处理器根本不会被触发，自然也不用管它的覆盖顺序。

## 8. 熔断降级：慢调用比例是怎么算的 + 熔断三态全流程

> 学习疑问：熔断触发后，是「全部请求都请求不到了」，还是「进一步降低允许请求的数量」？

### 8.1 `DegradeRule` 的三种策略

| grade | 策略 | 说明 |
|-------|------|------|
| `DEGRADE_GRADE_RT` | 慢调用比例 | 统计窗口内「慢调用」占比超过阈值 → 熔断 |
| `DEGRADE_GRADE_EXCEPTION_RATIO` | 异常比例 | 异常占比超过阈值 → 熔断 |
| `DEGRADE_GRADE_EXCEPTION_COUNT` | 异常数 | 一分钟内异常数超过阈值 → 熔断 |

**本项目用「慢调用比例」**（P5 计划「慢调用比例 > 20% 触发」）。

### 8.2 ⚠️ 关键坑：Sentinel 1.8.x 的 `count` 与 `slowRatioThreshold` 含义

很多教程按老版本写，容易写反。**Sentinel 1.8.x（本项目 1.8.8）里，`DEGRADE_GRADE_RT` 的字段含义是：**

- `count` = **慢调用 RT 阈值（毫秒）**：RT 超过它就算「慢调用」；
- `slowRatioThreshold` = **慢调用比例阈值（0~1）**：慢调用占比超过它就熔断。

所以「RT > 200ms 的慢调用占比 > 20% 触发熔断」的正确写法是：

```java
DegradeRule rule = new DegradeRule("seckill")
    .setGrade(RuleConstant.DEGRADE_GRADE_RT)
    .setCount(200)                // RT > 200ms 算慢调用
    .setSlowRatioThreshold(0.2)   // 慢调用比例阈值 20%
    .setMinRequestAmount(5)       // 统计窗口内至少 5 个请求才判定
    .setStatIntervalMs(1000)      // 统计窗口 1 秒
    .setTimeWindow(10);           // 熔断 10 秒后进入半开
DegradeRuleManager.loadRules(List.of(rule));
```

（老版本里 `count` 直接表示比例、且是「平均 RT」策略，语义完全不同。写代码前先确认 Sentinel 版本。）

### 8.3 熔断打开后：是「全部快速失败」，不是「降低数量」

**熔断一旦打开，所有请求都会被拦在方法体之外，直接走 `blockHandler` 返回 503，一个都不放行到真实业务逻辑（Redis/DB 根本不会被调用）。** 它不是「少放一点」，而是「彻底关闸」。

注意措辞：请求**能到达**服务、能到达方法的入口，但 Sentinel 在**进入方法体之前**就把它短路了，直接返回兜底。

**为什么是「全部拒绝」而不是「少放一点」？** 因为熔断挡的是「依赖坏了/变慢」，这时哪怕只放一个请求，它也会去碰那个坏掉的依赖、照样卡住、照样占线程。所以必须「彻底不碰它」，让它喘口气。

> 类比：水龙头漏水，限流是「把水流调小一点」（还在漏）；熔断是「直接把阀门关死」（完全不漏）。

### 8.4 熔断器的三态（不是永远全拒）

这是熔断器最核心的机制，`timeWindow=10`（秒）就是这里的开关：

```
① 关闭(正常)  ──慢调用比例 > 20%──►  ② 打开(熔断)
    ▲                                   │
    │                         等 10 秒(timeWindow)到
    │                                   ▼
    └────── 探测成功，恢复  ─────  ③ 半开(放 1 个探测请求)
                                     │
                                     └── 探测仍慢/失败 ──► 重新回到②打开
```

| 状态 | 行为 |
|---|---|
| **关闭**（正常） | 所有请求正常放行，正常执行方法 |
| **打开**（熔断中） | **所有请求快速失败**，返回 503，持续 `timeWindow`=10 秒 |
| **半开**（试探） | 10 秒到了，**只放 1 个「探测请求」**进去真实执行，看依赖恢复没有 |

- 探测请求**成功**（RT 正常了）→ 熔断器**关闭**，恢复全部放行；
- 探测请求**还是慢/失败** → 熔断器**重新打开**，再熔断 10 秒。

完整一句话：**熔断打开时「全部快速失败」，但过了一个时间窗（10 秒）会自动「半开」放一个探针请求试水，成功就恢复、失败就继续熔断。**

可用演示端点验证「半开」：触发熔断后等 10 秒以上，发一个 `delay=0` 的请求（模拟「依赖恢复」）→ 熔断器关闭恢复正常；发 `delay=300` 的请求（还是慢）→ 探测失败继续熔断。

### 8.5 限流 vs 熔断（一句话对比）

| | 限流 | 熔断 |
|---|---|---|
| 触发 | 流量超过阈值（QPS） | 依赖变慢/大量失败（慢调用比例） |
| 动作 | **放一部分、拒一部分**（持续） | **打开后全部拒绝**（一段时间），半开后试探 |
| 比喻 | 水龙头调小 | 阀门彻底关死，过会儿拧开一点试 |

## 9. 热点参数限流：按「商品 ID」维度限流

普通 `FlowRule` 对整个资源一刀切。秒杀场景里，某个「爆款商品」可能集中了绝大部分流量，希望**按参数（商品 ID）单独限流**，这就是热点参数限流 `ParamFlowRule`：

```java
ParamFlowRule rule = new ParamFlowRule("seckill")
    .setParamIdx(0)                       // 第 0 个参数 = seckillGoodsId
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(10)                         // 默认：任一商品 QPS 上限 10
    .setDurationInSec(1)
    .setParamFlowItemList(List.of(
        ParamFlowItem.newItem(1L, 5)      // 热点商品 id=1 单独收紧到 5 QPS
    ));
ParamFlowRuleManager.loadRules(List.of(rule));
```

要点：

- `paramIdx` 指向 `@SentinelResource` 方法参数的**下标**（从 0 开始），本项目 `seckill(Long seckillGoodsId, Long userId)` 里第 0 个就是商品 ID。
- `count` 是**默认阈值**（对所有非热点值生效），`ParamFlowItem` 里的 `count` 是**指定热点值的专属阈值**。
- `ParamFlowItem.newItem(1L, 5)` 里的 `1L` 必须与方法参数类型（Long）一致，Sentinel 按 `String.valueOf(arg)` 匹配。

> 热点参数限流依赖 `@SentinelResource` 注解把方法参数传给 Sentinel（普通 URL 资源拿不到方法参数），所以它天然和 `@SentinelResource` 绑定。

## 10. `@SentinelResource` 的 blockHandler 与 fallback 区别

`@SentinelResource` 是 Sentinel 的「注解式资源」入口，两个兜底方法别搞混：

```java
@SentinelResource(
    value = "seckill",            // 资源名（规则针对它配置）
    blockHandler = "seckillBlockHandler",  // 处理 BlockException（限流/熔断/热点）
    fallback = "seckillFallback"           // 处理业务异常（非 BlockException）
)
public Result<String> seckill(Long seckillGoodsId, Long userId) { ... }
```

| | `blockHandler` | `fallback` |
|---|---|---|
| 触发 | `BlockException`（FlowException / DegradeException / ParamFlowException 等） | 方法抛出的**其它异常**（业务异常） |
| 语义 | 「被规则挡住了」 | 「业务本身出错了」 |
| 签名 | 原方法参数 + 末尾 `BlockException` | 原方法参数 + 末尾 `Throwable` |

**常见误区**：熔断（`DegradeException`）是 `BlockException` 的子类，走的是 `blockHandler` 而不是 `fallback`。所以本项目在 `blockHandler` 里区分了熔断和限流：

```java
public Result<String> seckillBlockHandler(Long seckillGoodsId, Long userId, BlockException ex) {
    if (ex instanceof DegradeException) {
        return Result.fail(503, "秒杀服务熔断中，请稍后再试");   // 熔断
    }
    if (ex instanceof ParamFlowException) {
        return Result.fail(429, "该商品太火爆，请稍后再试");     // 热点限流
    }
    return Result.fail(429, "请求过于频繁，请稍后再试");         // 普通限流
}
```

> 本项目秒杀方法本身已妥善处理业务异常（内部捕获 + `GlobalExceptionHandler`），所以只加了 `blockHandler`、没加 `fallback`，避免改变原有业务异常的处理行为。

## 11. 规则加载的三种方式（P5 用第一种，P7 演进到第三种）

| 方式 | 规则存哪 | 改规则要不要重启 | 本项目 |
|------|----------|------------------|--------|
| **代码程序化** | Java 代码（`RuleManager.loadRules`） | 要改代码 + 重启 | ✅ P5 用这种 |
| **Dashboard 动态改** | 控制台内存 | 不用重启，但 Dashboard 重启后丢失 | 可选配合 |
| **Nacos 数据源** | Nacos Config | 不用重启、可持久化 | P7 再做 |

P5 选「代码程序化」的原因：**零额外依赖、可复现、JMeter 一压就生效**，最适合学习。代价是改阈值要改代码。P7 会把这些规则（连同 `jwt.secret`）迁到 Nacos Config，实现「改配置不重启」的动态刷新。

Sentinel Dashboard 是独立的可视化控制台（默认端口 8080，本项目因网关已占 8080 改用 8858），它和规则加载是**解耦**的：不启动 Dashboard，程序化规则照样生效；启动 Dashboard 只是为了看监控和动态改规则。

## 12. 怎么验证限流/熔断生效

### 前置

- 中间件就绪：MySQL(3307)、Redis(6379)、Nacos(8848)。
- 按 README 启动顺序启动 4 个服务（gateway 最后），统一入口 `http://localhost:8080`。

### 12.1 网关限流（QPS=100）

用 wrk / ab / JMeter 对秒杀下单接口打流量（需带合法 JWT），超过 100 QPS 的请求应返回 HTTP 429：

```bash
# 先登录拿 token（普通用户或管理员均可）
curl -X POST http://localhost:8080/api/admin/login \
     -H "Content-Type: application/json" \
     -d '{"username":"admin","password":"admin123"}'
# 返回体 data.token 即 JWT

# 单发确认正常（未超限，正常返回 code=200 或业务 code=500）
curl -X POST "http://localhost:8080/api/seckill/1" -H "Authorization: Bearer <token>"

# 高并发打（以 wrk 为例，-c 并发、-t 线程数），观察 429 比例
wrk -t20 -c500 -d10s --latency \
    -H "Authorization: Bearer <token>" \
    "http://localhost:8080/api/seckill/1"
```

> 注：把 QPS=100 压低到几（如临时改成 2）再压，更容易肉眼看到 429。

### 12.2 熔断（慢调用比例 > 20%）

用演示端点 `/api/seckill/demo/slow?delay=300`（delay 默认 300ms > 200ms 慢调用阈值），持续并发调用，慢调用占比超 20% 后熔断打开，返回 `code=503`：

```bash
# 并发打（需先触发统计窗口内 ≥5 个慢调用；单条循环速率太低时凑不满 minRequestAmount）
for i in $(seq 1 20); do
  curl -s "http://localhost:8080/api/seckill/demo/slow?delay=300" -H "Authorization: Bearer <token>"
  echo
  sleep 0.1
done
# 等 10 秒（timeWindow）后熔断器半开，再打一次试探：delay=0 恢复、delay=300 继续熔断
```

观察现象：前几次返回 `{"code":200,"msg":"慢调用模拟完成..."}`；慢调用比例超过 20% 后，后续请求秒回 `{"code":503,"msg":"演示资源已熔断..."}`（不再真正 sleep 300ms）。

### 12.3 热点参数限流（商品维度）

对同一商品 ID 高频秒杀下单，超过该商品的热点阈值（id=1 为 5 QPS）返回 `code=429`、`"该商品太火爆"`。

> 完整的 P2 数据正确性校验（不超卖/不多卖/不重复下单）见 `docs/P2-wrk-压测教程.md` 与 `docs/P2-check-data.sql`；P5 关注的是「限流/熔断是否按预期拦流量」，两者目标不同。
>
> 用 JMeter 做 P5 压测的完整实操（三环境隔离、测试计划搭建、三个场景、结果解读）见 `docs/P5-JMeter压测.md`。
