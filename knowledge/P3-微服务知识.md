# 微服务知识

> 本文件整理秒杀项目 P3 阶段「微服务拆分 + 注册发现 + 远程调用」涉及的通用知识点，作为学习笔记与面试复习材料。
> 代码工程对应 `monomer_seckill_backend/monomer_seckill_backend_cloud/`。

---

## 1. 微服务是怎么拆分的

拆分的本质：**把单体应用里按业务域划分的包，变成若干个能独立启动、独立部署、独立演进的应用。**

本项目从单体（`user` / `goods` / `cart` / `order` / `seckill` / `admin` / `merchant` / `common` / `config`）拆成 4 个模块：

| 模块 | 服务名 / 端口 | 职责 |
|------|--------------|------|
| `common-service` | 公共库（不注册） | 系统级基础设施：统一响应体、异常、用户上下文、认证、Redis 工具、CORS、MyBatis 字段填充 |
| `user-service` | `user-service` / 7001 | 人员相关：用户 + 管理员 + 商家 |
| `goods-order-service` | `goods-order-service` / 7002 | 业务紧密：商品 + 购物车 + 订单 |
| `seckill-service` | `seckill-service` / 7003 | 高并发隔离：秒杀（秒杀商品 + 库存 + 秒杀订单） |

每个服务都是**一个完整的独立应用**，各自拥有：启动类、`application.yml`（自己的端口 + `spring.application.name`）、实体/Mapper/Service/Controller。

> 原则：**公共模块只放跨服务复用的基础设施，不承载业务领域代码**；每个服务拥有自己用到的实体/Mapper/常量/Service/VO/Lua。共享库下个别表被多个服务访问时，各服务持自己的访问代码副本，换取独立演进（少量重复可接受）。

## 2. Maven 是怎么管理这几个模块的

这是 **Maven 多模块（聚合）工程**。最顶上的 `pom.xml` 同时扮演两个角色：

### 角色一：聚合器（把子模块串起来）

```xml
<packaging>pom</packaging>
<modules>
    <module>common-service</module>
    <module>user-service</module>
    <module>goods-order-service</module>
    <module>seckill-service</module>
</modules>
```

有了 `<modules>`，在根目录敲一次 `mvn package` 就会按依赖顺序构建全部子模块。

### 角色二：父 POM（给子模块继承公共配置）

每个子模块 pom 开头：

```xml
<parent>
    <groupId>com.example.seckill</groupId>
    <artifactId>monomer_seckill_backend_cloud</artifactId>
    <version>1.0.0</version>
</parent>
```

表示「继承父 pom 的 groupId / version / 属性（如 `java.version`）」。

### 关键：`dependencyManagement` vs `dependencies`

- **`<dependencyManagement>`**：只「登记版本」，**不真正引入依赖**。相当于一份版本价目表。
- **`<dependencies>`**：真正引入依赖。子模块要用什么，必须在自己 pom 里**再声明一次**（可省略版本，版本由父 pom 统一给）。

父 pom 里通过 `<dependencyManagement>` 引入两个 BOM（版本清单）：

```xml
<!-- Spring Cloud 版本清单 -->
<dependency>org.springframework.cloud:spring-cloud-dependencies:2023.0.3</dependency>
<!-- Spring Cloud Alibaba 版本清单（Nacos） -->
<dependency>com.alibaba.cloud:spring-cloud-alibaba-dependencies:2023.0.3.2</dependency>
```

目的是：**全工程所有模块的 Spring Boot / Spring Cloud / Spring Cloud Alibaba 版本统一**，避免版本打架。

> 再往上一层，父 pom 的 `<parent>` 是 `spring-boot-starter-parent`，负责提供 Spring Boot 版本与 Maven 打包插件默认配置。

## 3. Nacos 可视化界面

地址：**http://localhost:8848/nacos**，默认账号/密码 **nacos / nacos**。

进去后「服务管理 → 服务列表」能看到已注册的服务名（`user-service`、`goods-order-service`、`seckill-service`）及其实例数、IP、端口。

> 注意：Nacos 记录的是「服务名 → 实例 IP:端口」的映射，不是「注册了哪些类」；服务只有在启动成功后才会出现。本地 Nacos 跑在 WSL2 的 Docker 里（8848 是网页控制台端口，9848 是服务间 gRPC 端口），打不开时用 `wsl -d Ubuntu_Docker` 唤醒。

## 4. 服务名在哪里定义

服务名**不是**在 Nacos 配置里，而是 Spring Boot 核心属性 **`spring.application.name`**：

```yaml
spring:
  application:
    name: user-service          # ← 服务名在此定义
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848   # 这里只是 Nacos 服务器地址
```

Feign 里 `@FeignClient(name = "goods-order-service")` 的名字，必须与对方 yml 里的 `spring.application.name` 完全一致。

## 5. 为什么加了依赖 + 配了地址就能自动注册

四步：

1. **依赖里打包了 Nacos 客户端 SDK**：`spring-cloud-starter-alibaba-nacos-discovery` 传递引入 `nacos-client` 及自动配置类。
2. **Spring Boot 启动自动装配**：装配出 `NacosServiceRegistry`（负责注册）与 `NacosRegistration`（描述「我是谁、我住哪」）。
3. **Web 端口就绪后触发注册**：Spring Cloud 约定应用端口起来后自动调用 `serviceRegistry.register(...)`，等价于调用 SDK 的 `namingService.registerInstance("user-service", ip, port)`。
4. **发给 `server-addr` 指定的 Nacos**：Nacos 记下「服务名 → IP:端口」。

整个过程无需手写代码，也**不需要** `@EnableDiscoveryClient`（新版默认开启）。注册的是「服务名 + IP + 端口」一条实例记录。

## 6. 开启鉴权后怎么配置 Nacos 用户名密码

本地开源版 Nacos 默认 `nacos.core.auth.enabled=false`（关闭鉴权），所以注册/发现/配置都不需要账号密码。

若在 Nacos 服务端开启鉴权，客户端才需要补：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        username: nacos
        password: nacos
```

> `username/password` 即 Nacos 控制台登录账号，客户端用它换取 token 再调用。**apikey 不是 Nacos 注册发现的概念**，Nacos 走用户名/密码（内部转 token）。

## 7. Feign 的注册与调用方式

Feign 是声明式 HTTP 客户端，靠「服务名 + URL 路径」寻址：

- **提供方**：写 `@RestController` + `@RequestMapping`，暴露 HTTP 接口。
- **调用方**：写一个 `@FeignClient(name = "服务名")` 接口，方法上的 `@GetMapping/@PostMapping` 与提供方的 URL 对应。

```java
@FeignClient(name = "goods-order-service")   // 服务名 = 对方 spring.application.name
public interface GoodsOrderClient {
    @PostMapping("/internal/seckill-order/create/{id}")
    Result<String> createSeckillOrder(@PathVariable("id") Long id, ...);
}
```

底层是 **HTTP + JSON**，Feign 在运行时把接口调用翻译成 HTTP 请求，经 Nacos 服务发现找到实例后发出。

## 8. Dubbo 的注册与调用方式

Dubbo 是 RPC 框架，靠「**接口全限定类名**」寻址（不是服务名）：

- **契约**：双方共享同一个接口（放在公共 api 模块）。
- **提供方**：`@DubboService` 暴露实现。
- **调用方**：`@DubboReference` 注入远程代理，像本地类一样调用。

```java
// 共享接口
public interface StockService { long deduct(Long goodsId, Long userId); }

// 提供方
@DubboService
public class StockServiceImpl implements StockService { ... }

// 调用方
@DubboReference
private StockService stockService;   // 注入的是远程代理
```

**为什么调用方不用指定是哪个微服务？** 因为接口的全限定类名就是服务在注册中心的身份证：提供方按「接口类名」注册，调用方按「字段类型（接口类名）」查询，两边共享同一份接口 jar 保证类名一致，key 天然对得上。

## 9. Feign 与 Dubbo 的区别对比

| 维度 | Feign | Dubbo |
|------|-------|-------|
| 定位 | 声明式 HTTP 客户端 | 完整 RPC 框架 |
| 底层协议 | HTTP/1.1 | 自研二进制/TCP（或 Triple=HTTP/2） |
| 序列化 | JSON | Hessian2 / Protobuf 等 |
| 服务身份证 | `spring.application.name`（手动起名） | 接口全限定类名（自动由类型决定） |
| 调用方定位 | `@FeignClient(name=...)` 显式写服务名 | `@DubboReference` 看字段类型自动推导 |
| 契约 | 提供方 Controller + 调用方 Feign 接口（两份） | 双方共享同一份接口（一份） |
| 跨语言 | ✅ HTTP+JSON 通用 | 旧协议基本 Java；Triple 跨语言 |
| 可读/可调试 | ✅ 浏览器/curl 直接看 | ❌ 二进制，不可直读 |
| 适用 | 对外 API、通用 | Java 内部高性能、跨语言（Triple） |

核心心法：**框架（Feign/Dubbo）和协议（HTTP+JSON/二进制/HTTP2+protobuf）是两层**；跨不跨语言取决于协议+序列化，而非框架。

## 10. Dubbo 契约模块（标准用法）

跨服务接口与 DTO 抽到**独立的契约模块**（如 `seckill-api`），而不是塞进 `common-service`：

```
seckill-api（共享接口 + DTO）
   ├── StockService 接口
   └── dto/...          # 方法参数/返回值用到的对象（需实现 Serializable）

seckill-service（提供方）
   @DubboService public class StockServiceImpl implements StockService {...}

goods-order-service（调用方）
   @DubboReference private StockService stockService;
```

要点：

1. 共享的不只是接口，还有方法签名里的 **DTO**（且需可序列化）。
2. Dubbo 没有「路径」概念，身份是接口全限定类名。
3. 接口演进用 `version`/`group` 区分。
4. 真实微服务通常**内外两套**：对外 REST Controller（HTTP+JSON），对内 Dubbo。

> 基础设施（common-service）与业务契约（seckill-api）要分开，避免 common 又变成「什么都装」的公共模块。

## 11. 跨语言支持与 gRPC

- **Feign**：底层 HTTP+JSON 是通用格式，任何语言都能解析（Python 用 `requests` 即可），跨语言的是「协议」而非 Feign 库本身。
- **Dubbo**：旧 `dubbo://` + Hessian2 基本 Java 内部；Dubbo 3 的 **Triple 协议**基于 HTTP/2 + Protobuf、兼容 gRPC，可跨语言。
- **gRPC**：Google 开源的跨语言 RPC 框架，是跨语言 RPC 的事实标准。

### gRPC 概要

- 用 `.proto`（Protocol Buffers）定义服务与消息**一次**，生成多语言客户端/服务端代码。
- 底层 = **HTTP/2 + Protobuf**（二进制、紧凑、强类型）。
- 支持四种调用：一元、服务端流式、客户端流式、双向流式。
- 对比：Feign = HTTP/1.1+JSON（通用、可读），gRPC = HTTP/2+protobuf（高性能、强契约、跨语言），Dubbo 3 Triple ≈ 用 Dubbo 框架讲 gRPC 语言。

### 协议选型速查

| 场景 | 推荐 |
|------|------|
| 纯 Java 内部高性能 | Dubbo（dubbo:// 或 Triple） |
| 跨语言 + 通用 + 好调试 | HTTP + JSON（Feign/REST） |
| 跨语言 + 高性能 + 强类型 | gRPC / Protobuf（HTTP/2） |
| Java 内部又要留跨语言余地 | Dubbo 3 Triple |
