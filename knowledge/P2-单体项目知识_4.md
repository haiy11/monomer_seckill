## 1. Spring Boot 的自动装配机制

### 1.1 什么是自动装配

Spring Boot 的自动装配是指：框架根据类路径中的依赖、配置文件等条件，**自动创建和配置 Bean**，无需手动编写大量 XML 配置。

### 1.2 自动装配的触发入口

```java
@SpringBootApplication  // 启动类注解
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

`@SpringBootApplication` 包含三个核心注解：

| 注解 | 作用 |
|------|------|
| `@SpringBootConfiguration` | 表示这是一个配置类（本质是 `@Configuration`） |
| `@EnableAutoConfiguration` | **启用自动配置**，加载 `spring.factories` 中声明的配置类 |
| `@ComponentScan` | **自动扫描**当前包及子包下的所有组件（`@Service`、`@Controller` 等） |

### 1.3 自动装配的执行流程

```
1. 启动 SpringApplication.run()
   ↓
2. @ComponentScan 扫描当前包及子包
   - 扫描 @Configuration、@Service、@Controller 等注解
   ↓
3. @EnableAutoConfiguration 加载自动配置
   - 读取 META-INF/spring.factories 文件
   - 加载其中声明的自动配置类（如 RedisAutoConfiguration）
   ↓
4. 自动配置类根据条件注决定是否生效
   - @ConditionalOnClass：类路径中有指定类才生效
   - @ConditionalOnMissingBean：容器中没有指定 Bean 才创建
   ↓
5. 创建 Bean，注册到 Spring 容器
```

## 3. @Configuration 和 @Bean 的作用

### 3.1 @Configuration 注解

**作用：** 标记一个类为配置类，相当于传统的 XML 配置文件。Spring Boot 启动时会扫描并加载这个类。

```java
@Configuration  // 告诉 Spring：这是一个配置类
public class RedisConfig {
    // ...
}
```

### 3.2 @Bean 注解

**作用：** 将方法的返回值注册为 Spring 容器中的 Bean（对象）。Spring 启动时会调用这个方法，把返回值存入容器。

```java
@Configuration
public class RedisConfig {

    @Bean  // 将返回值注册为 Bean
    public RedisTemplate<String, Object> redisTemplate(
            RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        template.setKeySerializer(new StringRedisSerializer());
        template.setValueSerializer(new GenericJackson2JsonRedisSerializer());
        return template;  // 这个对象会被 Spring 容器管理
    }
}
```

### 3.3 @Bean 方法执行时机

- Spring 启动时**自动调用** `@Bean` 方法
- 方法参数由 Spring 自动注入（依赖注入）
- 返回值被 Spring 容器管理（单例）
- **只调用一次**

### 3.4 三种注册 Bean 的方式对比

| 方式 | 注解 | 使用位置 | 适用场景 |
|------|------|---------|---------|
| 组件扫描 | `@Service`、`@Component` 等 | 类上 | 自定义业务类，简单场景 |
| 配置类 | `@Bean` | 配置类的方法上 | 第三方库的类、需要复杂初始化的类 |
| 自动配置 | `@ConditionalOnMissingBean` + `@Bean` | 自动配置类的方法上 | 框架/第三方提供默认实现，允许用户覆盖 |

## 4. 为什么配置类能全局生效

### 4.1 核心原因：Spring 容器的 IoC + DI 机制

```
配置类创建对象 → 存入 Spring 容器 → 其他地方注入时从容器取出
```

### 4.2 详细流程

```
1. Spring 启动，扫描 @Configuration 类
   ↓
2. 发现 @Bean 方法 redisTemplate()
   ↓
3. 调用方法
   - 自动注入参数 RedisConnectionFactory factory
   - 执行方法体：new RedisTemplate()，设置序列化器
   - 返回 RedisTemplate 对象
   ↓
4. Spring 把返回的对象存入容器（单例）
   容器中：{ "redisTemplate": RedisTemplate@123456789 }
   ↓
5. 其他类注入时
   @Autowired
   private RedisTemplate<String, Object> redisTemplate;
   → Spring 从容器中取出 RedisTemplate@123456789
   → 注入的就是配置类创建的那个对象！
```

### 4.3 关键：单例模式

- 配置类 `@Bean` 方法只调用一次，只创建一个对象
- 这个对象被 Spring 容器管理，全局共享
- 所有注入的地方，拿到的都是**同一个对象**
- 因为是同一个对象，所以序列化器已经配置好了

## 5. 为什么我的配置能覆盖默认配置

### 5.1 @ConditionalOnMissingBean 注解

Spring Boot 的自动配置类中，默认 Bean 的创建方法上标注了 `@ConditionalOnMissingBean`：

```java
// Spring Boot 内部的 RedisAutoConfiguration
@Configuration
@ConditionalOnClass(RedisOperations.class)
public class RedisAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(name = "redisTemplate")  // 关键！
    public RedisTemplate<Object, Object> redisTemplate(
            RedisConnectionFactory factory) {
        RedisTemplate<Object, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        return template;
    }

    @Bean
    @ConditionalOnMissingBean  // 按类型匹配
    public StringRedisTemplate stringRedisTemplate(
            RedisConnectionFactory factory) {
        StringRedisTemplate template = new StringRedisTemplate();
        template.setConnectionFactory(factory);
        return template;
    }
}
```

### 5.2 覆盖机制执行流程

```
1. Spring 扫描用户的配置类 RedisConfig
   ↓
2. 注册 Bean 定义：redisTemplate → RedisConfig.redisTemplate()
   ↓
3. 加载 Spring Boot 自动配置类 RedisAutoConfiguration
   ↓
4. 检查 @ConditionalOnMissingBean(name = "redisTemplate")
   - 容器中已有名为 "redisTemplate" 的 Bean 定义（用户配置的）
   - 条件不满足，跳过默认 Bean 创建
   ↓
5. 最终使用用户的配置
```

### 5.3 加载顺序

```
用户配置类（@Configuration）优先加载
   ↓
Spring Boot 自动配置类后加载
   ↓
自动配置类检测到已有用户配置 → 跳过默认配置
```

## 6. Spring 容器就是一个大 Map

### 6.1 容器的本质

Spring 容器内部维护了一个 Map，存储所有 Bean：

```java
// Spring 容器内部（简化）
public class SpringContainer {
    private Map<String, Object> beans = new HashMap<>();

    // 注册 Bean
    public void registerBean(String name, Object bean) {
        beans.put(name, bean);
    }

    // 获取 Bean
    public Object getBean(String name) {
        return beans.get(name);
    }
}
```

### 6.2 配置类执行后的容器状态

```java
beans = {
    "redisTemplate": RedisTemplate@123456789,       // 用户配置类创建的
    "stringRedisTemplate": StringRedisTemplate@987654321,  // Spring Boot 自动配置的
    "tokenService": TokenService@555555555,         // @Service 创建的
    "redisConnectionFactory": LettuceConnectionFactory@777777777,
    // ...
}
```

### 6.3 注入时从容器取出

```java
@Service
public class MyService {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    // Spring 自动执行：
    // this.redisTemplate = container.getBean("redisTemplate");
    // this.redisTemplate = RedisTemplate@123456789（配置类创建的那个！）
}
```

## 7. Spring 注入的类默认都是单例

### 7.1 默认作用域：singleton

```java
@Service  // 默认 singleton
public class UserService { ... }
```

| 作用域 | 说明 | 使用场景 |
|--------|------|---------|
| **singleton**（默认） | 单例，整个应用只有一个实例 | 大部分情况 |
| prototype | 每次注入都创建新实例 | 很少用 |
| request | 每个 HTTP 请求一个实例 | Web 应用 |
| session | 每个 HTTP 会话一个实例 | Web 应用 |

### 7.2 验证单例

```java
@Service
public class UserService {
    public UserService() {
        System.out.println("UserService 创建，ID：" + this.hashCode());
    }
}

// 多个地方注入的都是同一个对象
// ServiceA 中：userService.hashCode() == 123456789
// ServiceB 中：userService.hashCode() == 123456789
```

## 8. Bean 的初始化时机

### 8.1 默认：启动时初始化（非懒加载）

```java
@Service  // 启动时就创建
public class UserService { ... }
```

```
启动项目...
  ↓
扫描所有 @Service、@Controller、@Component 等
  ↓
立即创建所有 Bean
  ↓
项目启动完成
```

### 8.2 懒加载：第一次使用时才初始化

```java
@Service
@Lazy  // 第一次使用时才创建
public class OrderService { ... }
```

```
启动项目...
  ↓
扫描所有 Bean
  ↓
不创建 OrderService（标记了 @Lazy）
  ↓
项目启动完成
  ↓
第一次调用 OrderService 的方法
  ↓
此时才创建 OrderService
```

### 8.3 @Autowired 和 @Resource 不是懒加载

注入的 Bean 已经在启动时创建好了，`@Autowired` 只是从容器中取出。

## 9. Spring 依赖初始化顺序算法

### 9.1 问题描述

配置类需要工厂参数，如果工厂还没初始化怎么办？

### 9.2 Spring 的解决方案：拓扑排序

```
第1步：扫描所有 Bean 定义
   - RedisConfig（需要 RedisConnectionFactory）
   - RedisConnectionFactory（Spring Boot 自动配置）
   - TokenService（需要 StringRedisTemplate）
   - UserController（需要 UserService）
   - ...

第2步：构建依赖图
   UserController → UserService → TokenService → StringRedisTemplate

第3步：拓扑排序（按依赖关系排序）
   1. RedisConnectionFactory（不依赖其他 Bean）
   2. StringRedisTemplate（不依赖其他 Bean）
   3. RedisTemplate（依赖 RedisConnectionFactory）
   4. TokenService（依赖 StringRedisTemplate）
   5. UserService（依赖 TokenService）
   6. UserController（依赖 UserService）

第4步：按顺序初始化
   1. 创建 RedisConnectionFactory
   2. 创建 StringRedisTemplate
   3. 创建 RedisTemplate（注入 RedisConnectionFactory）
   4. 创建 TokenService（注入 StringRedisTemplate）
   5. 创建 UserService（注入 TokenService）
   6. 创建 UserController（注入 UserService）
```

**关键：** Spring 会自动检测依赖关系，先初始化不依赖其他的 Bean，再初始化依赖已创建 Bean 的类。不会出现"依赖还没初始化"的情况。

### 9.3 配置类中工厂参数的来源

```java
@Bean
public RedisTemplate<String, Object> redisTemplate(
        RedisConnectionFactory factory) {  // 参数从哪来？
    // ...
}
```

- Spring Boot 自动配置创建了 `RedisConnectionFactory`
- Spring 调用 `redisTemplate()` 方法时，从容器中查找 `RedisConnectionFactory`
- 自动传入方法参数（依赖注入）

## 11. 配置类从系统启动到注入的完整流程

以 `RedisConfig` 为例：

```
1. Spring Boot 启动
   ↓
2. @ComponentScan 扫描到 RedisConfig（@Configuration）
   ↓
3. 发现 @Bean 方法 redisTemplate()

   ↓
8. 其他类注入 RedisTemplate
   @Autowired
   private RedisTemplate<String, Object> redisTemplate;

   → 注入的就是配置类创建的那个对象
   → 序列化器已经配置好了
```

## 12. 循环依赖问题

### 12.1 什么是循环依赖

```java
@Service
public class ServiceA {
    public ServiceA(ServiceB serviceB) { }  // A 依赖 B
}

@Service
public class ServiceB {
    public ServiceB(ServiceA serviceA) { }  // B 依赖 A
}
```

### 12.2 构造器注入的循环依赖（无法解决）

```
创建 ServiceA → 需要 ServiceB → 创建 ServiceB → 需要 ServiceA → 死锁！
```

**结果：** 启动报错

```
Error creating bean with name 'serviceA':
Requested bean is currently in creation: Is there an unresolvable circular reference?
```

### 12.3 字段注入为什么可以解决循环依赖

Spring 使用**三级缓存**机制解决字段注入的循环依赖：

| 缓存级别 | 名称 | 作用 |
|---------|------|------|
| 一级缓存 | `singletonObjects` | 存储完全初始化好的 Bean |
| 二级缓存 | `earlySingletonObjects` | 存储已创建但未完全初始化的 Bean（半成品） |
| 三级缓存 | `singletonFactories` | 存储 Bean 工厂对象，用于生成早期 Bean |

**字段注入解决循环依赖的过程：**

```
第1步：创建 ServiceA，调用构造器（不需要依赖）
   ↓
第2步：ServiceA 对象创建成功，但字段未注入
   ↓
第3步：将 ServiceA（半成品）放入三级缓存
   ↓
第4步：注入 ServiceB（发现需要 ServiceB）
   ↓
第5步：创建 ServiceB，调用构造器（不需要依赖）
   ↓
第6步：ServiceB 对象创建成功，但字段未注入
   ↓
第7步：将 ServiceB（半成品）放入三级缓存
   ↓
第8步：注入 ServiceA（发现需要 ServiceA）
   ↓
第9步：从三级缓存中获取 ServiceA（半成品）
   - 找到了！将 ServiceA 提升到二级缓存
   ↓
第10步：ServiceB 注入 ServiceA（半成品引用）
   ↓
第11步：ServiceB 初始化完成，放入一级缓存
   ↓
第12步：ServiceA 注入 ServiceB（已完成）
   ↓
第13步：ServiceA 初始化完成，放入一级缓存
```

**关键：**
- 字段注入先创建对象（调用构造器），再注入字段
- 构造器注入在创建对象时就需要依赖，无法提前暴露半成品
- 所以字段注入可以解决循环依赖，构造器注入不能

### 12.4 @Lazy 如何解决构造器循环依赖

```java
@Service
public class ServiceA {
    public ServiceA(@Lazy ServiceB serviceB) { }  // 懒加载
}

@Service
public class ServiceB {
    public ServiceB(ServiceA serviceA) { }
}
```

**@Lazy 的工作原理：**

```
第1步：创建 ServiceA
   ↓
第2步：发现需要 ServiceB，但标记了 @Lazy
   ↓
第3步：Spring 不创建真正的 ServiceB
   - 创建一个 ServiceB 的代理对象（CGLIB 代理）
   - 代理对象看起来像 ServiceB，但内部是空的
   ↓
第4步：将代理对象注入到 ServiceA
   - ServiceA 创建完成
   ↓
第5步：创建 ServiceB
   - 注入 ServiceA（已经创建好了）
   - ServiceB 创建完成
   ↓
第6步：第一次调用 ServiceB 的方法时
   - 代理对象才创建真正的 ServiceB
```

**关键：**
- `@Lazy` 创建的是**代理对象**（占位符）
- 代理对象延迟了 Bean 的真正创建
- 只需要在一个地方加 `@Lazy` 就可以解决循环依赖
- 不会报错，因为注入的是代理对象，不是真正的 Bean

## 13. Bean 的覆盖机制

### 13.1 Spring Boot 2.1+ 默认禁止覆盖

```yaml
# application.yml
spring:
  main:
    allow-bean-definition-overriding: false  # 默认 false
```

### 13.2 冲突场景

```java
// 方式1：@Service
@Service
public class TokenService { ... }

// 方式2：配置类
@Configuration
public class MyConfig {
    @Bean
    public TokenService tokenService() { ... }
}
```

**结果：** 启动报错！

```
Error creating bean with name 'tokenService':
The bean 'tokenService', defined in class path resource [MyConfig.class],
could not be registered.
A bean with that name has already been defined in file [.../TokenService.class]
and overriding is disabled.
```

### 13.3 允许覆盖

```yaml
spring:
  main:
    allow-bean-definition-overriding: true
```

允许覆盖时，`@Bean` 优先级高于 `@Service`。

### 13.4 覆盖优先级

```
@Bean（配置类）> @Service、@Component 等注解
```

## 14. Spring Boot 自动配置中的条件注解

### 14.1 @ConditionalOnMissingBean

**作用：** 容器中没有指定 Bean 时才创建

```java
@Bean
@ConditionalOnMissingBean(name = "redisTemplate")  // 按名称匹配
public RedisTemplate<Object, Object> redisTemplate(...) {
    // 如果容器中没有名为 "redisTemplate" 的 Bean，才创建
}

@Bean
@ConditionalOnMissingBean  // 按类型匹配
public StringRedisTemplate stringRedisTemplate(...) {
    // 如果容器中没有 StringRedisTemplate 类型的 Bean，才创建
}
```

### 14.2 条件注解家族

| 注解 | 作用 | 示例 |
|------|------|------|
| `@ConditionalOnMissingBean` | 容器中没有指定 Bean 时才创建 | 覆盖默认配置 |
| `@ConditionalOnBean` | 容器中有指定 Bean 时才创建 | 依赖其他 Bean |
| `@ConditionalOnClass` | 类路径中有指定类时才创建 | 依赖第三方库 |
| `@ConditionalOnMissingClass` | 类路径中没有指定类时才创建 | 可选依赖 |
| `@ConditionalOnProperty` | 配置属性满足条件时才创建 | 根据配置开关功能 |
| `@ConditionalOnExpression` | SpEL 表达式为 true 时才创建 | 复杂条件 |

### 14.3 条件注解的使用位置

- **方法上：** 控制单个 Bean 是否创建
- **类上：** 控制整个配置类是否加载

```java
@Configuration
@ConditionalOnClass(RedisOperations.class)  // 类上：控制整个配置类
public class RedisAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(name = "redisTemplate")  // 方法上：控制单个 Bean
    public RedisTemplate<Object, Object> redisTemplate(...) { }
}
```

## 15. Bean 的条件注册和允许覆盖的区别

### 15.1 条件注册（@ConditionalOnMissingBean）

```
用户配置类先注册 Bean 定义
   ↓
自动配置类检查条件 → 发现已存在 → 跳过创建
   ↓
不会产生冲突（因为自动配置类根本没创建）
```

### 15.2 允许覆盖（allow-bean-definition-overriding）

```
@Service 先创建 Bean
   ↓
@Bean 也创建同名 Bean
   ↓
覆盖之前的 Bean（需要开启 allow-bean-definition-overriding=true）
```

### 15.3 对比

| 机制 | 是否报错 | 谁生效 | 使用场景 |
|------|---------|--------|---------|
| 条件注册 | 不报错 | 先注册的生效 | Spring Boot 自动配置 |
| 允许覆盖 | 不报错（需开启） | 后注册的覆盖先注册的 | 手动覆盖 |
| 禁止覆盖（默认） | 报错 | 无 | 默认行为 |

### 15.4 为什么 @ConditionalOnMissingBean 不会冲突

- `@ConditionalOnMissingBean` 在**注册阶段**就判断了
- 如果发现已有 Bean 定义，**根本不会注册**，不会产生冲突
- 而覆盖机制是在**两个 Bean 都注册后**才产生冲突

## 16. 三种注解的本质区别

### 16.1 组件注解（定义阶段）

```java
@Service       // 服务层
@Component     // 通用组件
@Repository    // 数据访问层
@Controller    // 控制器
```

**作用：** 标记类，告诉 Spring "这是一个组件，需要管理"。Spring 扫描时自动发现并注册为 Bean。

**本质：定义类的注解，定义好了被扫描到后续再创建类。**

### 16.2 @Bean 注解（创建阶段）

```java
@Configuration
public class MyConfig {
    @Bean
    public MyService myService() {
        return new MyService();
    }
}
```

**作用：** 标记配置类中的方法，让 Spring 根据被标记的方法来创建类。

**本质：标记配置类中创建类的方法，让 Spring 框架根据被标记的方法来创建类。**

### 16.3 @ConditionalOnMissingBean（判断阶段）

```java
@Bean
@ConditionalOnMissingBean(name = "myService")
public MyService myService() {
    return new MyService();
}
```

**作用：** 在创建类前判断要不要创建这个类。

**本质：配置类中创建类前判断要不要创建类的注解。**

### 16.4 三者关系

```
@Service（定义）→ Spring 扫描 → 注册 Bean 定义
                                        ↓
@Bean（创建）→ Spring 扫描 → 定义创建 Bean 的方法
                                        ↓
@ConditionalOnMissingBean（判断）→ 检查条件 → 决定是否创建
                                        ↓
@Autowired（注入）→ 从容器取出 → 注入到需要的地方
```

## 17. 为什么配置类不能管理构造注解标记的类的创建

### 17.1 问题

如果类上加了 `@Service`，同时又写了配置类 `@Bean`，会怎样？

### 17.2 执行顺序

```
第1步：Spring 扫描 @Service 类
   - 注册 Bean 定义：tokenService → TokenService.class
   ↓
第2步：创建 TokenService Bean（通过 @Service）
   - 容器中已有 tokenService Bean
   ↓
第3步：扫描配置类
   - 发现 @Bean 方法，名称也是 "tokenService"
   - 检查 @ConditionalOnMissingBean(name = "tokenService")
   - 发现已存在（@Service 创建的）
   - 跳过配置类的 Bean 创建
   ↓
结果：使用 @Service 创建的 Bean，配置类被忽略
```

### 17.3 如果不加 @ConditionalOnMissingBean

```
@Service 创建了 tokenService Bean
   ↓
@Bean 也想创建 tokenService Bean
   ↓
两个同名 Bean 冲突 → 报错！（Spring Boot 2.1+ 默认禁止覆盖）
```

### 17.4 结论

- `@Service` 和 `@Bean` 是两种**互斥**的注册方式
- 一个类只用一种方式注册
- **不要同时使用！**

| 注册方式 | 适用场景 |
|---------|---------|
| 只用 `@Service` | 自定义业务类，简单场景 |
| 只用 `@Bean` | 需要复杂初始化、第三方库的类 |
| `@Bean` + `@ConditionalOnMissingBean` | 提供默认实现，允许用户覆盖 |

## 18. Spring Boot 自动配置的核心原理

### 18.1 spring.factories 文件

第三方库在 `META-INF/spring.factories` 中声明自动配置类：

```properties
# META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
org.springframework.boot.autoconfigure.data.redis.RedisAutoConfiguration
```

### 18.2 自动配置类的结构

```java
@Configuration
@ConditionalOnClass(RedisOperations.class)        // 类路径有 Redis 才加载
@EnableConfigurationProperties(RedisProperties.class)  // 绑定配置属性
public class RedisAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(name = "redisTemplate")  // 用户没配置才创建
    public RedisTemplate<Object, Object> redisTemplate(
            RedisConnectionFactory factory) {
        // 默认实现
    }

    @Bean
    @ConditionalOnMissingBean  // 用户没配置才创建
    public StringRedisTemplate stringRedisTemplate(
            RedisConnectionFactory factory) {
        // 默认实现
    }
}
```

### 18.3 核心设计理念：约定优于配置

1. **开箱即用**：引入依赖就能用，不需要任何配置
2. **灵活定制**：写配置类覆盖默认配置
3. **避免冲突**：`@ConditionalOnMissingBean` 确保不重复创建

### 18.4 用户覆盖第三方默认配置的完整流程

```
1. 第三方库的类不加 @Service
   ↓
2. 第三方库通过配置类 + @ConditionalOnMissingBean 创建 Bean
   ↓
3. 用户写配置类，创建同名 Bean
   ↓
4. Spring 先加载用户配置类，创建 Bean
   ↓
5. Spring 后加载第三方自动配置类
   ↓
6. 检查 @ConditionalOnMissingBean → 发现已存在 → 跳过
   ↓
7. 最终使用用户的配置
```

### 18.5 自己实现可覆盖的组件

```java
// 1. 类不加 @Service
public class SmsService {
    private final String apiKey;
    public SmsService(String apiKey) {
        this.apiKey = apiKey;
    }
}

// 2. 默认配置类
@Configuration
public class SmsAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(name = "smsService")  // 允许覆盖
    public SmsService smsService() {
        return new SmsService("default-api-key");
    }
}

// 3. 用户覆盖
@Configuration
public class CustomSmsConfig {
    @Bean
    public SmsService smsService() {
        return new SmsService("custom-api-key");
    }
}
```

## 19. 注入方式对比

### 19.1 三种注入方式

| 注入方式 | 代码 | 推荐度 | 特点 |
|---------|------|--------|------|
| **构造器注入** | 构造器参数 | 推荐 | 不可变（final），易于测试 |
| 字段注入 | `@Autowired` 字段 | 不推荐 | 难以测试 |
| Setter 注入 | `@Autowired` setter 方法 | 一般 | 可选依赖 |

### 19.2 构造器注入示例

```java
@RestController
public class UserController {
    private final UserService userService;  // final，不可变

    public UserController(UserService userService) {  // 构造器注入
        this.userService = userService;
    }
}
```

**优势：**
- 依赖关系明确
- 不可变（`final`）
- 不需要 `@Autowired` 注解（Spring 4.3+ 自动注入）
- 易于单元测试

## 20. 知识点速查表

| 知识点 | 核心内容 |
|--------|---------|
| **自动装配** | `@EnableAutoConfiguration` 加载 `spring.factories` 中的配置类 |
| **@Configuration** | 标记配置类，Spring 启动时扫描 |
| **@Bean** | 将方法返回值注册为 Spring 容器中的 Bean |
| **全局生效** | 配置类创建的对象存入容器（单例），其他地方注入的是同一个对象 |
| **覆盖默认配置** | `@ConditionalOnMissingBean` 检测到用户配置后跳过默认创建 |
| **Spring 容器** | 本质是一个大 Map，存储所有 Bean |
| **单例模式** | 默认所有 Bean 都是单例，全局共享 |
| **初始化时机** | 默认启动时初始化，`@Lazy` 延迟到第一次使用 |
| **依赖顺序** | 拓扑排序，先创建不依赖其他的，再创建依赖的 |
| **循环依赖** | 字段注入可通过三级缓存解决，构造器注入不能 |
| **@Lazy** | 创建代理对象，延迟真正创建，解决构造器循环依赖 |
| **Bean 覆盖** | Spring Boot 2.1+ 默认禁止，需 `allow-bean-definition-overriding=true` |
| **@ConditionalOnMissingBean** | 容器中没有指定 Bean 时才创建，用于覆盖机制 |
| **@Service** | 定义类的注解，标记后由 Spring 扫描创建 |
| **@Bean** | 创建类的方法注解，让 Spring 根据方法创建类 |
| **自动配置核心** | 约定优于配置：开箱即用 + 灵活定制 + 避免冲突 |
