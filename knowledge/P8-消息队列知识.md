# P8 异步削峰解耦（RabbitMQ + 死信队列）

> 阶段目标：秒杀下单改「Redis 预扣 → MQ 异步落库」，把瞬时高并发削成后端可承受的匀速写入；
> 用**死信队列（DLX）**替代定时轮询，实现「下单后 15 分钟未支付自动取消 + 库存回补」。
>
> 核心演示点：**请求线程不再等待数据库写，秒回订单号；订单超时由消息 TTL 到期自动触发，无需定时任务扫库。**

---

## 一、为什么要消息队列

秒杀场景的经典问题：瞬时几十万请求同时打到「扣库存 + 插订单」这一步，数据库扛不住。

| 痛点 | 没有 MQ | 有 MQ |
|------|--------|-------|
| 削峰 | 请求线程直接写 DB，DB 连接被瞬时打满 | 请求只发消息即返回，DB 写入由消费者按固定并发慢慢消化 |
| 解耦 | 下单与落库强耦合在一个同步调用里 | 生产者只管「预扣 + 发消息」，消费者只管「落库」，互不阻塞 |
| 异步 | 用户等 DB 写完才收到响应 | 用户秒回订单号，订单在后台异步创建 |

**削峰的本质**：把「无法控制的瞬间尖峰」变成「可以控制的匀速流量」。MQ 就是一个缓冲池，
生产者的速度由流量决定，消费者的速度由并发数/prefetch 决定，两者解耦。

---

## 二、RabbitMQ 核心概念

| 概念 | 含义 | 本项目取值 |
|------|------|-----------|
| **Exchange**（交换机） | 接收生产者消息，按路由规则分发到队列 | `seckill.order.exchange`（direct） |
| **Queue**（队列） | 存储消息的缓冲区，消费者从这里取 | 下单队列 / 延迟队列 / 死信（超时）队列 |
| **Binding**（绑定） | 交换机与队列的关联关系 | 用 routing key 绑定 |
| **Routing Key**（路由键） | 交换机据此把消息路由到匹配的队列 | `seckill.order.create` / `.delay` / `.timeout` |

direct 交换机按 routing key **精确匹配**：消息的 routing key 等于绑定的 routing key 才投递。

> 记忆点：**生产者只认识交换机，消费者只认识队列**，中间靠 binding + routing key 连接。

## 三、本项目 P8 落地拓扑

```
秒杀请求（seckill-service）
   │ ① Redis Lua 预扣（判库存+判重复+扣库存+记用户）
   │ ② 预生成 orderNo → 发消息（发布确认）→ 立即返回 orderNo
   ▼
seckill.order.exchange (direct)
   ├─ routingKey = seckill.order.create
   │    → seckill.order.queue          —— 下单队列
   │        └ SeckillOrderCreateListener：DB 扣库存 + 落订单（异步、受控并发）
   │            └ 建单成功 → 发「超时消息」到 delay 路由，消息带 TTL=15min
   │
   └─ routingKey = seckill.order.delay
        → seckill.order.delay.queue     —— 延迟队列（x-dead-letter-* 指向 timeout 路由）
             │（15 分钟后消息过期，变成「死信」自动重新投递）
             ▼
        routingKey = seckill.order.timeout
        → seckill.order.timeout.queue   —— 死信（超时）队列
             └ SeckillOrderTimeoutListener：订单仍待支付 → 关闭 + 回补库存
```

调用链（P8 前 vs P8 后）：

| | 请求线程做了什么 | DB 写在哪 |
|---|---|---|
| P8 前 | 校验 → Redis 预扣 → **同步 DB 扣减 + 插订单** → 返回 | 请求线程 |
| P8 后 | 校验 → Redis 预扣 → **发消息 → 返回 orderNo** | 消息消费者线程 |

## 四、死信队列（DLX）实现「延时任务」

RabbitMQ 没有内置延时队列，标准做法是 **「TTL + DLX」**：

1. **延迟队列**声明时带上两个参数：
   - `x-dead-letter-exchange`：消息过期后转投到哪个交换机；
   - `x-dead-letter-routing-key`：转投时用哪个 routing key。
2. 生产者发送消息时设置 `expiration`（TTL，毫秒）。
3. 消息在延迟队列里**不被消费**，只等待过期；过期后被 RabbitMQ 当作「死信」，
   按上面的两个参数重新投递到目标队列（死信队列）。
4. 死信队列的消费者拿到消息时，已经过了 TTL 时长——这就是「15 分钟后触发」。

> **逐条消息 TTL 的坑（实测踩过）**：RabbitMQ 只在消息到达**队头**时才移除过期消息。
> 若同一个延迟队列里混用了不同 TTL，短 TTL 消息排在长 TTL 消息后面，就不会按时过期（队头阻塞）。
> 本项目所有超时消息 TTL 统一为 15 分钟、按发送顺序依次过期，因此不受影响；
> 但规则是：**不要在同一个延迟队列里混用不同 TTL**。需要不同延时就用多个延迟队列。

对应到本项目：下单成功后发一条 `expiration = 15分钟` 的超时消息到延迟队列；15 分钟后它
「死」掉，自动进入超时队列，超时消费者判断订单还是「待支付」就关闭并回补库存。

> 一句话：**把「时间」编码成「消息 TTL」，把「到点执行」交给 RabbitMQ 的死信机制，省掉定时任务。**

本项目 P8 前用的是 `@Scheduled` 每 30 秒扫描 `status=待支付 AND create_time < now-15min`，
P8 后删掉了这个定时任务，改成 DLX。对比：

| | 定时扫描 | 死信队列 |
|---|---|---|
| 触发方式 | 轮询，固定间隔全表扫 | 消息到期推送，精确到单条 |
| 时效性 | 最多延迟一个扫描周期 | TTL 到期即触发 |
| 资源 | 周期性 SQL 扫描 | 无扫描，MQ 内部处理 |
| 适用 | 兜底/批量 | 精确延时、削峰 |

## 五、消息可靠性：一条消息的「不丢」链路

P8 同时演示了生产端、Broker、消费端三段的可靠性：

### 5.1 生产端：发布确认（publisher confirm）

```java
// 发送时带上 CorrelationData（关联一个 messageId）
CorrelationData cd = new CorrelationData(messageId);
rabbitTemplate.convertAndSend(exchange, key, message, cd);
// 阻塞等待 Broker 确认（confirm.isAck()），确认成功才返回
cd.getFuture().get(3, TimeUnit.SECONDS);
```

- 配置 `spring.rabbitmq.publisher-confirm-type: correlated`；
- Broker 确认「消息已落盘」后 `getFuture()` 才返回 ack；失败/超时抛异常，
  调用方回滚 Redis 预扣，保证「预扣了就不会丢消息」。

### 5.2 Broker：交换机/队列/消息持久化

- 交换机、队列都声明为 `durable`（`QueueBuilder.durable(...)` / `new DirectExchange(..., true, false)`）；
- 消息默认 `deliveryMode=PERSISTENT`（Spring AMQP 默认持久化）。

这样 Broker 重启后队列与消息还在。

### 5.3 消费端：消费确认 + 幂等

- `acknowledge-mode: auto`：监听器**正常返回 = ack**（消息从队列删除），**抛异常 = reject**；
- 默认 `requeue`：reject 的消息重新入队、再次投递，实现「处理失败自动重试」。

> 正因为「至少一次投递」可能重复，消费者必须**幂等**（见第六节）。

## 六、消费者幂等设计

RabbitMQ 只保证**至少一次投递**（at-least-once），不保证只投一次，所以消费端要能安全重放：

| 场景 | 处理 | 结果 |
|------|------|------|
| 同一条下单消息重复投递 | 先查 `orderNo` 是否已存在，存在则跳过建单 | 不重复扣库存/插订单 |
| 同一用户重复下单（唯一索引兜底） | 捕获 `DuplicateKeyException`，回滚 Redis 预扣后 ack | 不产生脏数据 |
| DB 库存不足等业务失败 | 回滚 Redis 预扣，记录日志后 ack（不重试） | 不空转重试 |
| 超时消息重复投递 | 关闭前校验 `status=待支付` 且更新行数>0，否则跳过 | 回补库存只发生一次 |

回补库存本身也幂等：Redis 侧 Lua 用 `SREM` 判断用户是否在已购集合、DB 侧 `restoreStock`
只对「确实关闭成功」的订单执行一次。

## 七、JSON 序列化（替代 Java 原生序列化）

RabbitTemplate 默认用 Java 原生序列化（`SimpleMessageConverter`），有安全风险、不可读、跨语言难。
本项目改用 `Jackson2JsonMessageConverter`：

```java
@Bean
public Jackson2JsonMessageConverter jackson2JsonMessageConverter(ObjectMapper objectMapper) {
    return new Jackson2JsonMessageConverter(objectMapper);
}
```

- 用 Spring Boot 自动配置的 `ObjectMapper`（含 JavaTime 模块），BigDecimal/LocalDateTime 都能正确序列化；
- 消息体附带 `__TypeId__` 头记录目标类型，监听器据此反序列化回 `SeckillOrderMessage` 等 DTO；
- Spring Boot 会自动把该转换器装配到 `RabbitTemplate` 和监听器容器工厂，两侧一致。

好处：在 RabbitMQ 管理台（`:15672`）能直接看到 JSON 消息内容，排查方便。

## 九、常见坑

1. **消息发出去消费者收不到**：检查 binding 的 routing key 是否与发送时一致；
   检查延迟队列的 `x-dead-letter-routing-key` 是否等于超时队列的绑定 key。
2. **改了队列参数不生效**：RabbitMQ 队列声明后参数不可变，改了 TTL/死信参数需先删旧队列
   （或改队列名），否则会报 `PRECONDITION_FAILED - inequivalent arg`。
3. **消息被拒后无限重试**：监听器抛异常且 `requeue` 时，消息会反复重投形成死循环。
   处理：业务失败**内部消化后 ack**（不抛），只有真正的瞬时故障才抛异常重试。
4. **JSON 反序列化报 `JsonMappingException`**：转换器与两侧 DTO 字段不匹配，或类路径不一致；
   确保 DTO 有无参构造（Lombok `@NoArgsConstructor`）。
5. **`__TypeId__` 找不到类**：默认信任所有包，若生产环境限制 `trustedPackages` 要包含 DTO 所在包。
6. **publisher confirm 没回调**：没配 `publisher-confirm-type: correlated`，或用了旧版 API
   `setConfirmCallback`（新版用 `CorrelationData#getFuture()`）。
7. **连接不上 RabbitMQ**：确认 host/port/vhost/账号，管理台 `:15672` 用同账号可登录；
   注意 vhost 要显式写 `/`（默认）。
8. **幂等没做好导致重复扣库存**：消费者第一步必须先按 orderNo 判重，而不是上来就扣库存。
