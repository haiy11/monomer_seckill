# P8 异步削峰解耦（RabbitMQ + 死信队列）

> 阶段目标：秒杀下单改「Redis 预扣 → MQ 异步落库」，把瞬时高并发削成后端可承受的匀速写入；
> 用**死信队列（DLX）**替代定时轮询，实现「下单后 15 分钟未支付自动取消 + 库存回补」。
>
> 核心演示点：**请求线程不再等待数据库写，秒回订单号；订单超时由消息 TTL 到期自动触发，无需定时任务扫库。**

---

## 一、为什么要消息队列

秒杀场景的经典问题：瞬时几十万请求同时打到「扣库存 + 插订单」这一步，数据库扛不住。

| 痛点 | 没有 MQ | 有 MQ |
|------|--------|-------|
| 削峰 | 请求线程直接写 DB，DB 连接被瞬时打满 | 请求只发消息即返回，DB 写入由消费者按固定并发慢慢消化 |
| 解耦 | 下单与落库强耦合在一个同步调用里 | 生产者只管「预扣 + 发消息」，消费者只管「落库」，互不阻塞 |
| 异步 | 用户等 DB 写完才收到响应 | 用户秒回订单号，订单在后台异步创建 |

**削峰的本质**：把「无法控制的瞬间尖峰」变成「可以控制的匀速流量」。MQ 就是一个缓冲池，
生产者的速度由流量决定，消费者的速度由 `concurrency`/`prefetch` 决定（见第六节），两者解耦。

---

## 二、RabbitMQ 核心概念

### 2.1 四个概念

| 概念 | 含义 | 本项目取值 |
|------|------|-----------|
| **Exchange**（交换机） | 接收生产者消息，按路由规则分发到队列，**只路由、不存消息** | `seckill.order.exchange`（direct） |
| **Queue**（队列） | 真正**存储消息**的缓冲区，消费者从这里取 | 下单队列 / 延迟队列 / 死信（超时）队列 |
| **Binding**（绑定） | 交换机与队列之间的**关联规则**，规则里含一个 binding key | 用 routing key 绑定 |
| **Routing Key**（路由键） | 挂在**消息**上的字符串，交换机据此匹配路由 | `seckill.order.create` / `.delay` / `.timeout` |

### 2.2 最容易混的一点：Routing Key 不是实体上的标记

初学最大的误区是把 Routing Key 当成「Exchange / Queue 身上的标记」。其实它**既不属于交换机，
也不属于队列**，而是分两处出现：

| 名称 | 归属 | 作用 |
|---|---|---|
| **Routing Key**（路由键） | 挂在**消息**上 | 生产者发送时指定，如 `seckill.order.create` |
| **Binding Key**（绑定键） | 挂在 **Binding** 上 | 交换机用它和消息的 routing key 做匹配的规则 |

所以四个概念的关系是：

> **生产者**把消息（带 routing key）交给 **Exchange**；**Exchange** 拿这条消息的 routing key，
> 去和它名下每一条 **Binding** 上写的 binding key 比对；匹配上哪条 Binding，就把消息投递到那条
> Binding 指向的 **Queue**。

### 2.3 快递分拣中心类比

| 概念 | 类比 |
|---|---|
| **Exchange** | 分拣中心（自己不存货，只按规则把包裹分到不同货架） |
| **Queue** | 各个货架（真正放包裹的地方，快递员从货架取件） |
| **Binding** | 分拣规则（"凡是单子上写『上海』的，送到 1 号货架"） |
| **Routing Key** | 包裹单上的目的地（寄件人发货时贴上去的） |

关键就在这句：**Routing Key 是贴在「包裹（消息）」上的，不是贴在货架或分拣中心上的。** 分拣中心
（Exchange）看的是「包裹上的目的地」，再对照「分拣规则（Binding）」决定往哪个货架（Queue）送。

### 2.4 一条消息的投递链路

```
生产者 Producer
   │  发送消息，同时给消息打上 routing key = "seckill.order.create"
   ▼
┌────────────────────────────────────────────────────────┐
│              Exchange（交换机，只路由、不存消息）           │
│   ① 收到消息，取出它的 routing key                        │
│   ② 在自己的「绑定表」里找：谁的 binding key 和它匹配？      │
│   ③ 找到目标队列，投递过去                                 │
└────────────────────────────────────────────────────────┘
   │  匹配成功，投递
   ▼
┌──────────────────┐
│   Queue（队列）    │  ← 消息在这里排队存着，等消费者来取
│  seckill.order.queue │
└──────────────────┘
   │
   ▼
消费者 Consumer（从这里把消息拿走处理）
```

一个交换机名下可以登记多条 Binding（每条 = 一个 binding key + 一个目标队列），这就是「一个交换机
支撑多个队列」的原因。direct 交换机按 routing key **精确匹配**；此外还有 topic（通配符）、fanout
（广播、忽略路由键）、headers（按消息头匹配）三种类型，本项目用的是 direct。

> 记忆点：**生产者只认识「交换机 + 路由键」，消费者只认识「队列」**，中间靠 binding + binding key 连接。

## 三、本项目 P8 落地拓扑

### 3.1 主链路（一条自上而下的单向流）

```
                          秒杀请求  POST /api/seckill/1
                                     │
                                     │ ① Redis 预扣库存（Lua 原子扣减）
                                     │ ② 发「下单消息」（routing key = seckill.order.create）
                                     ▼
                        ┌──────────────────────────┐
                        │     下单队列               │
                        │  seckill.order.queue      │
                        └────────────┬─────────────┘
                                     │ 消费者监听这里
                                     │ DB 扣库存 + 落订单（建单成功）
                                     │ ③ 发「超时消息」（routing key = seckill.order.delay）
                                     ▼
                        ┌──────────────────────────┐
                        │     延迟队列               │
                        │ seckill.order.delay.queue │
                        │ 消息 expiration = 15 分钟   │
                        │（没有消费者，只当计时器）     │
                        └────────────┬─────────────┘
                                     │ ④ 15 分钟后过期，RabbitMQ 自动当作「死信」
                                     │    按 x-dead-letter-exchange / routing-key 重新投递
                                     ▼
                        ┌──────────────────────────┐
                        │   死信（超时）队列          │
                        │ seckill.order.timeout.queue│
                        └────────────┬─────────────┘
                                     │ 消费者监听这里，先查订单状态：
                                     │   · 仍待支付   → 关闭(status=3) + 回补库存
                                     │   · 已支付/已取消 → 直接跳过
                                     ▼
                                 处理完成
```

三条「发消息」走的是**同一个交换机** `seckill.order.exchange`，只是路由键不同：

| 谁发 | 发的消息 | routing key | 最终进哪个队列 |
|---|---|---|---|
| 秒杀请求（SeckillService） | 下单消息 | `seckill.order.create` | 下单队列 |
| 下单消费者建单成功后（CreateListener） | 超时消息 | `seckill.order.delay` | 延迟队列 |
| RabbitMQ 死信自动投递 | 同一条超时消息 | `seckill.order.timeout` | 超时队列 |

### 3.2 同步支付旁路：支付不走任何队列

```
用户付款  POST /api/seckill/order/{orderNo}/pay
   │  同步 HTTP，直接执行 SQL
   ▼
UPDATE seckill_order SET status = 1 WHERE order_no = ? AND status = 0
   （订单 0→1，与 MQ 完全无关，延迟队列里的超时消息照旧躺着）
```

整体是「**一条 MQ 主链路**（下单 → 延迟 → 死信超时）+ **一条同步支付旁路**（直改 DB）」，
两条路互不干扰，最终靠「超时消费者到点后自查订单状态」来保证不误关已支付订单。

### 3.3 调用链（P8 前 vs P8 后）

| | 请求线程做了什么 | DB 写在哪 |
|---|---|---|
| P8 前 | 校验 → Redis 预扣 → **同步 DB 扣减 + 插订单** → 返回 | 请求线程 |
| P8 后 | 校验 → Redis 预扣 → **发消息 → 返回 orderNo** | 消息消费者线程 |

## 四、死信队列（DLX）实现「延时任务」

RabbitMQ 没有内置延时队列，标准做法是 **「TTL + DLX」**：

1. **延迟队列**声明时带上两个参数：
   - `x-dead-letter-exchange`：消息过期后转投到哪个交换机；
   - `x-dead-letter-routing-key`：转投时用哪个 routing key。
2. 生产者发送消息时设置 `expiration`（TTL，毫秒）。
3. 消息在延迟队列里**不被消费、没有消费者**，只是躺着等待过期；过期后**由 RabbitMQ 服务端自动**
   把它当作「死信」，按上面的两个参数重新投递到目标队列（死信队列）。
4. 死信队列的消费者拿到消息时，已经过了 TTL 时长——这就是「15 分钟后触发」。

> 关键澄清：延迟队列的消费者数是 **0**，没有程序去「消费」它；不是「自己消费掉超时消息」，
> 而是「**消息到期后由 RabbitMQ 自动搬走、重新路由**」，整个过程没有消费者参与。

### 4.1 支付了为什么也不取消延迟消息

你可能会想：用户都支付了，那条超时消息留着不是浪费吗？这正是这种方案**简单、可靠**的地方：

1. MQ 消息一旦发出，很难「精准取消」（要取消得再发取消消息，或引入延迟插件/扫描，复杂且易漏）；
2. 所以干脆**不取消**，让超时消息照常到期；
3. 到期后，超时消费者**不盲目执行**，而是**先查订单当前状态**再决定：

```
超时消费者收到消息
   ├─ 查订单：不存在？         → 直接跳过
   ├─ 查订单：已支付/已取消？   → 直接跳过（UPDATE 影响 0 行，不动库存）
   └─ 查订单：还是待支付？     → 关闭(status=3) + 回补库存
```

这一步「先查状态、满足条件才动作」就是**幂等 + 条件触发**。核心思想：**消息可能会重复、可能会迟到，
但消费端永远基于「当前真实状态」来判断，而不是盲信消息本身。**

> 一句话：**把「时间」编码成「消息 TTL」，把「到点执行」交给 RabbitMQ 的死信机制，省掉定时任务。**

### 4.2 逐条消息 TTL 的坑（实测踩过）

RabbitMQ 只在消息到达**队头**时才移除过期消息。若同一个延迟队列里混用了不同 TTL，短 TTL 消息排在
长 TTL 消息后面，就不会按时过期（队头阻塞）。本项目所有超时消息 TTL 统一为 15 分钟、按发送顺序依次
过期，因此不受影响；但规则是：**不要在同一个延迟队列里混用不同 TTL**。需要不同延时就用多个延迟队列。

### 4.3 对比：定时扫描 vs 死信队列

本项目 P8 前用 `@Scheduled` 每 30 秒扫描 `status=待支付 AND create_time < now-15min`，P8 后删掉了
这个定时任务，改成 DLX：

| | 定时扫描 | 死信队列 |
|---|---|---|
| 触发方式 | 轮询，固定间隔全表扫 | 消息到期推送，精确到单条 |
| 时效性 | 最多延迟一个扫描周期 | TTL 到期即触发 |
| 资源 | 周期性 SQL 扫描 | 无扫描，MQ 内部处理 |
| 适用 | 兜底/批量 | 精确延时、削峰 |

## 五、消息可靠性：一条消息的「不丢」链路

P8 同时演示了生产端、Broker、消费端三段的可靠性。

### 5.1 生产端：发布确认（publisher confirm）

**要解决什么问题**：Redis 已经预扣库存了，如果消息其实没发出去，用户被扣了库存却没生成订单，必须回滚。
所以生产端要「确认消息真的到了 Broker」再返回成功。

```java
// ① 真正「发消息」：这一行把消息帧 basic.publish 发给 Broker
CorrelationData cd = new CorrelationData(messageId);
rabbitTemplate.convertAndSend(exchange, key, message, cd);

// ② 阻塞「等回执」：这一行不发送任何东西，只是等 Broker 的确认
CorrelationData.Confirm confirm = cd.getFuture().get(3, TimeUnit.SECONDS);
if (confirm == null || !confirm.isAck()) {
    throw new BizException("秒杀下单消息投递未确认");
}
```

**两行代码分别干了什么**（这里是最容易混的地方）：

- `convertAndSend(...)`：**真正发请求**，把消息（`basic.publish` 帧）发出去，并带上 `CorrelationData`。
- `getFuture().get(3, SECONDS)`：**不发任何请求**，只是阻塞当前线程、坐在那里等「之前那次发送」的确认回来。

**CorrelationData 是什么**：发布确认的「**回执单号**」。生产者可能并发发很多消息，Broker 每条都会回
ack，`CorrelationData` 用一个唯一 id（我们用的 `messageId`）把「我发的这条消息」和「Broker 回的那条
ack」对应起来。它是**可选参数**，不传也能发，只是发完不知道结果、无法做回滚兜底。

**`isAck() == true` 的确切含义**：Broker 在告诉你「**这条消息我已经接收并接手了**」。对我们这种
「持久化交换机 + 持久化队列 + 持久化消息」的组合，ack 意味着消息**已经落到队列里（持久化）**，接下来
是消费者的事，与生产者无关。这也就是我们能放心 `return Result.ok(orderNo)` 的原因。

**为什么 `sendCreateOrder` 方法没有 `throws`**：Java 里 `throws` 只对「受检异常」（`IOException`、
`InterruptedException` 等）强制要求；`get(...)` 抛的 `InterruptedException`/`ExecutionException`/
`TimeoutException` 都是受检异常，但它们在 `awaitConfirm` 内部被 catch 后**转换成了 `BizException`**
（`extends RuntimeException`，非受检）再抛出，所以方法签名不用声明 `throws`；而外面的
`catch (Exception e)` 仍能接住它（因为 `RuntimeException` 是 `Exception` 的子类），从而回滚 Redis。

### 5.2 Broker：交换机/队列/消息持久化

- 交换机、队列都声明为 `durable`（`QueueBuilder.durable(...)` / `new DirectExchange(..., true, false)`）；
- 消息默认 `deliveryMode=PERSISTENT`（Spring AMQP 默认持久化）。

这样 Broker 重启后队列与消息还在。

### 5.3 消费端：推模式 + 消费确认

**是 MQ 推给消费者，不是消费者主动拉**：

| 模式 | 谁主动 | 本项目用哪种 |
|---|---|---|
| 推（push） | Broker 主动推给消费者，消费者注册订阅 | ✅ `@RabbitListener` |
| 拉（pull） | 消费者主动问「有没有消息」（`rabbitTemplate.receive()`） | ❌ 没用 |

**`@RabbitListener` 到底做了什么**：它把方法注册成「队列的回调」。服务启动时，Spring AMQP 会：

```
创建监听容器 → 连 Broker → 发 basic.consume（"我要消费 seckill.order.queue"）
   → Broker 登记该消费者 → 之后队列一来消息，Broker 就主动推过来
   → Spring 把 JSON 反序列化成 SeckillOrderMessage → 调用 onCreate(message)
```

方法的参数类型（`SeckillOrderMessage`）决定消息如何反序列化，必须和发送侧类型一致。

**消费确认（ack）**：

- `acknowledge-mode: auto`：监听器**正常返回 = ack**（消息从队列删除），**抛异常 = reject**；
- 默认 `requeue`：reject 的消息重新入队、再次投递，实现「处理失败自动重试」。

> 正因为「至少一次投递」可能重复，消费者必须**幂等**（见第七节）。

## 六、削峰的节奏控制：concurrency / prefetch / max-concurrency

用「**银行柜台**」类比这三个参数（它们管的是「消费者按什么节奏消化消息」）：

| MQ 概念 | 银行类比 |
|---|---|
| 队列里的消息 | 大厅里排队的客户 |
| Broker | 叫号系统 |
| 消费者（一个线程） | 一个柜台窗口 |
| `concurrency` | 常开几个窗口（= 同时几个窗口在办业务） |
| `prefetch` | 每个窗口前面最多排几张「已叫号」的等候椅 |
| `ack` | 业务办完、客户离开，叫号系统再叫下一位补位 |
| `max-concurrency` | 高峰期最多临时再加开几个窗口的上限 |

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 4        # 常开 4 个窗口（同时 4 个线程在处理）
        max-concurrency: 16   # 最忙时最多扩到 16 个窗口
        prefetch: 50          # 每个窗口前面等候椅最多 50 张
```

**三个参数分别管什么**：

- `concurrency = 4`：**同时真正在处理**的消息数 = 4（一个消费者线程 = 一个窗口，一次只处理 1 条）。
- `prefetch = 50`：**每个窗口**最多从队列「预取」50 条到本地缓冲（还没 ack 的）。窗口仍是一次办 1 件，
  办完 ack 一件，Broker 再推 1 件补位，缓冲始终保持 ≤ 50。
- `max-concurrency = 16`：Spring AMQP 在「当前窗口都很忙」时自动加窗口，最多加到 16，闲了再收回。

**数字走一遍**（瞬间涌入 1000 条）：

```
队列里 1000 条在排队
   ├─ 4 个窗口各被推 50 条 = 共 200 条「在途」（4 × 50）
   │   但真正在办的只有 4 条（concurrency）
   ├─ 窗口办完 1 条 → ack → 补推 1 条（保持 50 缓冲）
   └─ 大厅还剩 1000 - 200 = 800 条没被推出来，慢慢排队
```

**为什么这么配能削峰**：DB 才是瓶颈。无论生产者一秒发 1 万还是 10 万条，消费者永远是「4 个窗口、
一次 4 条」地慢慢写 DB，多出来的消息在队列里排队——「峰」被「削」成了平地。

**prefetch 大小取舍**：

| prefetch | 效果 |
|---|---|
| 1 | 办一件、ack 一件、再拿一件 → 最严格最均衡，但每次等 Broker 补货有往返延迟，吞吐偏低 |
| 50（本项目） | 窗口手里有点缓冲，不用每次等补货，吞吐更高，同时配合 concurrency 控制 DB 写入速率 |
| 很大 | 缓冲太大，多个消费者抢同一队列时，可能某个消费者「囤」太多导致不均衡 |

> 一句话：**`concurrency` = 几个窗口（同时办几件）；`prefetch` = 每个窗口手边最多预拿几件（在途缓冲）；
> `max-concurrency` = 最多加几个窗口。三者一起把「瞬间峰值」变成「按窗口能力匀速消化」。**

## 七、消费者幂等设计

RabbitMQ 只保证**至少一次投递**（at-least-once），不保证只投一次，所以消费端要能安全重放：

| 场景 | 处理 | 结果 |
|------|------|------|
| 同一条下单消息重复投递 | 先查 `orderNo` 是否已存在，存在则跳过建单 | 不重复扣库存/插订单 |
| 同一用户重复下单（唯一索引兜底） | 捕获 `DuplicateKeyException`，回滚 Redis 预扣后 ack | 不产生脏数据 |
| DB 库存不足等业务失败 | 回滚 Redis 预扣，记录日志后 ack（不重试） | 不空转重试 |
| 超时消息重复投递 | 关闭前校验 `status=待支付` 且更新行数>0，否则跳过 | 回补库存只发生一次 |

回补库存本身也幂等：Redis 侧 Lua 用 `SREM` 判断用户是否在已购集合、DB 侧 `restoreStock`
只对「确实关闭成功」的订单执行一次。

## 八、JSON 序列化（替代 Java 原生序列化）

RabbitTemplate 默认用 Java 原生序列化（`SimpleMessageConverter`），有安全风险、不可读、跨语言难。
本项目改用 `Jackson2JsonMessageConverter`：

```java
@Bean
public Jackson2JsonMessageConverter jackson2JsonMessageConverter(ObjectMapper objectMapper) {
    return new Jackson2JsonMessageConverter(objectMapper);
}
```

- 用 Spring Boot 自动配置的 `ObjectMapper`（含 JavaTime 模块），BigDecimal/LocalDateTime 都能正确序列化；
- 消息体附带 `__TypeId__` 头记录目标类型，监听器据此反序列化回 `SeckillOrderMessage` 等 DTO；
- Spring Boot 会自动把该转换器装配到 `RabbitTemplate` 和监听器容器工厂，两侧一致。

好处：在 RabbitMQ 管理台（`:15672`）能直接看到 JSON 消息内容，排查方便。

## 九、RabbitMqConfig 配置类

这个类做的是「**声明拓扑 + JSON 转换器**」，注意「连接」不是它做的：

| 职责 | 谁干的 | 依据 |
|---|---|---|
| 连接 MQ（host/端口/账号/密码/vhost） | Spring Boot 自动配置的 `ConnectionFactory` | Nacos 里 `spring.rabbitmq.*` |
| 声明拓扑（Exchange/Queue/Binding） | `RabbitMqConfig` 里的 `@Bean` | 下面这张表 |
| 声明 JSON 转换器 | `RabbitMqConfig` 里的 `@Bean` | `jackson2JsonMessageConverter` |
| 把声明真正在 MQ 服务器上创建出来 | Spring Boot 自动配置的 `RabbitAdmin` | 启动时扫描声明式 Bean 并 `declare` |

`RabbitMqConfig` 里的 `@Bean` 只是「定义要有什么」，真正执行 `exchange.declare`/`queue.declare`/
`queue.bind` 的是 `RabbitAdmin`——所以服务一启动，管理台就自动冒出队列和交换机，无需手动建。

| Bean 方法 | 返回类型 | 作用 |
|---|---|---|
| `seckillOrderExchange()` | `DirectExchange` | 定义直连交换机 `seckill.order.exchange` |
| `seckillOrderQueue()` | `Queue` | 定义下单队列 |
| `seckillOrderDelayQueue()` | `Queue` | 定义延迟队列，**并带上死信参数** |
| `seckillOrderTimeoutQueue()` | `Queue` | 定义死信（超时）队列 |
| `seckillOrderCreateBinding(...)` | `Binding` | `create` 路由键 → 下单队列 |
| `seckillOrderDelayBinding(...)` | `Binding` | `delay` 路由键 → 延迟队列 |
| `seckillOrderTimeoutBinding(...)` | `Binding` | `timeout` 路由键 → 超时队列 |
| `jackson2JsonMessageConverter(...)` | `Jackson2JsonMessageConverter` | 消息体 JSON 序列化 |

延迟队列那一行是死信队列的关键：

```java
@Bean
public Queue seckillOrderDelayQueue() {
    return QueueBuilder.durable(SeckillMqConstants.ORDER_DELAY_QUEUE)
            .deadLetterExchange(SeckillMqConstants.ORDER_EXCHANGE)      // 过期后丢回主交换机
            .deadLetterRoutingKey(SeckillMqConstants.ORDER_TIMEOUT_KEY) // 用 timeout 路由键
            .build();
}
```

它声明延迟队列时顺手挂了两个参数，告诉 RabbitMQ：「这个队列里的消息过期后，当成死信，重新投到主交换机、
路由键用 `seckill.order.timeout`」——于是过期消息自动进了超时队列。

## 十一、常见坑

1. **消息发出去消费者收不到**：检查 binding 的 routing key 是否与发送时一致；
   检查延迟队列的 `x-dead-letter-routing-key` 是否等于超时队列的绑定 key。
2. **改了队列参数不生效**：RabbitMQ 队列声明后参数不可变，改了 TTL/死信参数需先删旧队列
   （或改队列名），否则会报 `PRECONDITION_FAILED - inequivalent arg`。
3. **消息被拒后无限重试**：监听器抛异常且 `requeue` 时，消息会反复重投形成死循环。
   处理：业务失败**内部消化后 ack**（不抛），只有真正的瞬时故障才抛异常重试。
4. **JSON 反序列化报 `JsonMappingException`**：转换器与两侧 DTO 字段不匹配，或类路径不一致；
   确保 DTO 有无参构造（Lombok `@NoArgsConstructor`）。
5. **`__TypeId__` 找不到类**：默认信任所有包，若生产环境限制 `trustedPackages` 要包含 DTO 所在包。
6. **publisher confirm 没回调**：没配 `publisher-confirm-type: correlated`，或用了旧版 API
   `setConfirmCallback`（新版用 `CorrelationData#getFuture()`）。
7. **连接不上 RabbitMQ**：确认 host/port/vhost/账号，管理台 `:15672` 用同账号可登录；
   注意 vhost 要显式写 `/`（默认）。
8. **幂等没做好导致重复扣库存**：消费者第一步必须先按 orderNo 判重，而不是上来就扣库存。
9. **混用不同 TTL 导致延时不准**：同一延迟队列里混用不同 TTL，短 TTL 消息会卡在长 TTL 消息后面（队头阻塞）。
10. **误以为支付要「取消」延迟消息**：正确做法是支付直改 DB、不碰延迟队列，靠超时消费者到期后自查订单状态。
