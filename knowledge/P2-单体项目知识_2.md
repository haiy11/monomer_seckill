## 1. 构造器注入的完整原理

### 1.1 依赖注入不是单个注解完成的

以 `AdminController` 为例：

```java
@RestController
public class AdminController {
    private final AdminService adminService;

    public AdminController(AdminService adminService) {
        this.adminService = adminService;
    }
}
```

依赖注入是**三个部分协同工作**的结果：

| 参与方 | 作用 |
|--------|------|
| `@RestController` | 让 `AdminController` 成为 Spring 容器管理的 Bean |
| 构造函数 | Spring 通过调用构造函数，将依赖传入 |
| `@Service`（在 `AdminService` 上） | 让 `AdminService` 成为可注入的 Bean |

### 1.2 Spring 4.3+ 单构造函数自动注入

从 **Spring Framework 4.3** 开始，如果一个类只有一个构造函数，Spring 会**自动使用它进行依赖注入**，无需额外的 `@Autowired` 注解。

> 本项目使用 Spring Boot 3.3.5，对应 Spring Framework 6.1.x，远超 4.3 的最低要求。

### 1.3 版本对应关系

| Spring Boot 版本 | Spring Framework 版本 |
|------------------|----------------------|
| 1.x              | 4.x                  |
| 2.x              | 5.x                  |
| 3.x              | 6.x                  |

### 1.4 完整注入流程

```
1. Spring 启动
       ↓
2. 扫描组件（@RestController、@Service 等）
       ↓
3. 发现 AdminController（因为有 @RestController）
       ↓
4. 发现 AdminService（因为有 @Service）
       ↓
5. 创建 AdminService 实例
       ↓
6. 通过构造函数将 AdminService 注入到 AdminController
       ↓
7. AdminController 初始化完成
```

### 1.5 注入的本质：谁负责创建对象

**依赖注入只是改变了"谁来创建对象"**：

```java
// 传统方式：自己创建
public AdminController() {
    this.adminService = new AdminService();  // 我自己 new
}

// 依赖注入：Spring 创建并传入
public AdminController(AdminService adminService) {
    this.adminService = adminService;  // Spring 帮我创建并传入
}
```

注入 ≠ 不需要实例化。对象还是必须创建的，只是创建的责任从开发者转移给了 Spring。

## 2. `@RequiredArgsConstructor` 自动生成构造函数

### 2.1 为什么需要 Lombok

手动编写构造函数的痛点：当依赖增多或修改时，需要同步维护构造函数，容易遗漏。

```java
// 手动编写：每次增删依赖都要改构造函数
@Service
public class AdminService {
    private final UserService userService;
    private final UserMapper userMapper;
    private final GoodsMapper goodsMapper;

    // 手动维护，容易遗漏
    public AdminService(UserService userService, UserMapper userMapper, GoodsMapper goodsMapper) {
        this.userService = userService;
        this.userMapper = userMapper;
        this.goodsMapper = goodsMapper;
    }
}
```

### 2.2 使用 `@RequiredArgsConstructor`

```java
@Service
@RequiredArgsConstructor  // Lombok 自动生成构造函数
public class AdminService {
    private final UserService userService;
    private final UserMapper userMapper;
    private final GoodsMapper goodsMapper;

    // 不需要手动写构造函数！
}
```

Lombok 在**编译时**自动生成包含所有 `final` 字段的构造函数，等价于上面的手写代码。

### 2.3 Lombok 编译时生成原理

```
源代码（.java）
    ↓  Lombok 注解处理器介入
    ↓  在编译阶段修改 AST（抽象语法树）
编译后的 .class
    ↓  包含自动生成的构造函数
```

- **编译时生成**：不影响运行时性能
- **生成的代码与手写完全一致**：Spring 无感知，正常调用构造函数

## 3. `@RequiredArgsConstructor` vs `@Autowired` 字段注入

### 3.1 两种方式对比

#### 构造器注入（`@RequiredArgsConstructor` + `final`）

```java
@Service
@RequiredArgsConstructor
public class AdminService {
    private final UserService userService;  // final 保证不可变
    private final UserMapper userMapper;
}
```

#### 字段注入（`@Autowired` 直接加在字段上）

```java
@Service
public class AdminService {
    @Autowired
    private UserService userService;  // 非 final，依赖隐藏

    @Autowired
    private UserMapper userMapper;
}
```

### 3.2 注入机制对比

| 特性 | `@RequiredArgsConstructor` | `@Autowired` 字段注入 |
|------|---------------------------|----------------------|
| **生成时机** | 编译时（Lombok 生成构造函数代码） | 运行时 |
| **注入方式** | Spring 正常调用构造函数 | Spring 使用反射直接设置字段值 |
| **反射使用** | 仅用于查找构造函数，然后正常调用 | 完全依赖反射（`field.set()`） |
| **字段选择** | 只注入 `final` 字段 | 注入所有 `@Autowired` 标记的字段 |
| **编译时检查** | ✅ 有（方法不存在会编译错误） | ❌ 无（运行时才发现） |
| **安全性** | 高 | 低 |

### 3.3 字段注入的反射过程

```java
// @Autowired 字段注入的内部过程：
// 1. Spring 调用无参构造函数创建对象
AdminService instance = new AdminService();

// 2. Spring 使用反射直接设置字段值
Field field = AdminService.class.getDeclaredField("userService");
field.setAccessible(true);       // 突破 private 限制
field.set(instance, userService); // 直接写入字段
```

### 3.4 Spring 官方推荐

Spring 官方明确推荐**构造器注入**，原因：
- 依赖明确（构造函数签名一目了然）
- 不可变（`final` 保证线程安全）
- 易于单元测试（直接 `new` 传入 Mock）
- 编译时检查（减少运行时错误）

## 4. `@RequiredArgsConstructor` 为什么不会注入不需要的类

### 4.1 核心规则：只为 `final` 字段生成构造函数参数

```java
@RequiredArgsConstructor
public class AdminService {
    // ✅ 会注入：有 final
    private final UserService userService;
    private final UserMapper userMapper;

    // ❌ 不会注入：非 final
    private String tempValue;

    // ❌ 不会注入：static final
    private static final String CONST = "test";

    // ❌ 不会注入：非 final（即使只赋值一次）
    private UserService optionalService;
}
```

Lombok 生成的构造函数：

```java
// 只包含 final 字段
public AdminService(UserService userService, UserMapper userMapper) {
    this.userService = userService;
    this.userMapper = userMapper;
}
```

### 4.2 `final` 是控制开关

| 字段声明 | 是否被注入 | 原因 |
|----------|-----------|------|
| `private final UserService userService;` | ✅ 是 | 有 `final` 关键字 |
| `private UserService userService;` | ❌ 否 | 无 `final` 关键字 |
| `private static final String CONST = "test";` | ❌ 否 | `static final` 是类常量，不参与实例构造 |
| `private String cache = "default";` | ❌ 否 | 无 `final`，有初始值 |

### 4.3 "事实不可变"不会被 Lombok 识别

Java 中存在"事实不可变"概念（变量只赋值一次后再未修改），但 Lombok **不识别**这种模式：

```java
@RequiredArgsConstructor
public class AdminService {
    // 没有 final，即使只赋值一次，Lombok 也不会为它生成构造函数参数
    private UserService userService;
}
```

**原因**：
1. **编译时机**：Lombok 在编译时处理注解，"事实不可变"是运行时行为，无法在编译时判断
2. **判断困难**：编译器无法确定一个非 `final` 字段是否真的只被赋值一次
3. **明确约定**：`final` 是明确的编译时标记，Lombok 可以简单可靠地识别

## 5. `final` 关键字的四大作用

### 5.1 不可变性

```java
private final UserService userService;  // 注入后不可修改

public void someMethod() {
    userService = null;  // ❌ 编译错误！防止意外修改
}
```

### 5.2 线程安全

`final` 字段有特殊的 Java 内存模型保证：
- 在构造函数完成后，对所有线程**立即可见**
- 不需要同步机制就能保证可见性

```java
// final 字段：构造完成后所有线程可见，线程安全
private final UserService userService;

// 非 final 字段：可能存在可见性问题，需要额外同步
private UserService userService;
```

### 5.3 明确依赖关系

```java
public class AdminService {
    private final UserService userService;  // ✅ 必须依赖，编译时检查
    private String optionalCache;           // 可选字段，可以为 null
}
```

### 5.4 防止空指针

```java
// final + 构造器注入：保证不为 null
private final UserService userService;

// 字段注入：可能为 null（如果忘记加 @Autowired）
@Autowired
private UserService userService;
```

## 6. 单例 Bean 与高并发：`final` 不会成为性能瓶颈

### 6.1 Spring Bean 默认是单例

```java
@Service  // 默认单例，整个应用只有一个实例
public class AdminService {
    private final UserService userService;
}
```

### 6.2 单例不会成为瓶颈的前提：无状态设计

关键区分**无状态 Bean** vs **有状态 Bean**：

#### 无状态 Bean（线程安全 ✅）

```java
@Service
@RequiredArgsConstructor
public class AdminService {
    // 只有 final 依赖，没有可变的实例变量
    private final UserService userService;
    private final OrderService orderService;

    public User getUser(Long id) {
        return userService.findById(id);  // 线程安全
    }
}
```

**为什么线程安全**：
- `final` 依赖：只读，多线程共享安全
- 方法内的局部变量：每个线程独立，在栈内存中
- 无共享可变状态：没有竞争条件

```
线程1: adminService.getUser(1) → userService.findById(1)  // 局部变量在栈上
线程2: adminService.getUser(2) → userService.findById(2)  // 局部变量在栈上
// 互不干扰
```

#### 有状态 Bean（线程不安全 ❌）

```java
@Service
public class AdminService {
    private List<User> userCache = new ArrayList<>();  // ❌ 共享可变状态
    private int requestCount = 0;                      // ❌ 共享可变状态

    public void addUser(User user) {
        userCache.add(user);  // ❌ ArrayList 不是线程安全的
    }

    public void incrementCount() {
        requestCount++;  // ❌ 非原子操作，高并发下丢失更新
    }
}
```

### 6.3 如果必须有状态，使用线程安全容器

```java
@Service
public class AdminService {
    // ✅ 使用线程安全的集合
    private final ConcurrentHashMap<Long, User> userCache = new ConcurrentHashMap<>();
    private final AtomicInteger requestCount = new AtomicInteger(0);

    public void incrementCount() {
        requestCount.incrementAndGet();  // ✅ 原子操作
    }
}
```

### 6.4 单例性能对比

| 方式 | 实例创建 | 内存占用 | 线程安全 | 性能 |
|------|---------|---------|---------|------|
| 单例 + 无状态 | 只创建一次 | 一个实例 | ✅ 安全 | ✅ 高 |
| 每次请求创建新实例 | 频繁创建 | 频繁 GC | ✅ 安全 | ❌ 低 |

**Spring 的设计理念：单例 + 无状态 = 高性能 + 线程安全**

## 7. 为什么使用其他类的方法必须先实例化

### 7.1 类 vs 对象

- **类** = 模板/图纸（不能直接使用）
- **对象** = 实例/实体（可以使用）
- **实例化** = 根据"图纸"创建"实体"

```java
// UserService.class 是"图纸"，不能直接用
public class UserService {
    private UserMapper userMapper;  // 每个对象有自己的数据

    public User findById(Long id) {
        return userMapper.selectById(id);  // 方法需要访问对象的成员变量
    }
}

// 必须先创建对象
UserService userService = new UserService();  // 实例化
User user = userService.findById(1L);         // 使用
```

### 7.2 方法为什么依赖对象

非静态方法需要访问对象的成员变量（如 `userMapper`），如果没有对象，成员变量就不存在，方法无法执行。

```java
// 两个不同的对象，可能有不同的依赖
UserService service1 = new UserService();
service1.setUserMapper(mapper1);  // 使用 mapper1

UserService service2 = new UserService();
service2.setUserMapper(mapper2);  // 使用 mapper2

// 如果直接用类调用，用哪个 mapper？
UserService.findById(1L);  // 编译错误！不知道用哪个对象的 userMapper
```

### 7.3 依赖注入的本质

注入只是把 `new` 的工作交给了 Spring，对象还是必须创建的：

```
1. Spring 扫描到 @Service 注解的类
       ↓
2. 创建 UserService 对象（实例化）
       ↓
3. 创建 AdminService 对象（实例化）
       ↓
4. 通过构造函数将 UserService 注入到 AdminService
       ↓
5. 注入完成，可以使用了
```

## 8. 最佳实践总结

### 8.1 Service / Controller 层

```java
@Service
@RequiredArgsConstructor
public class AdminService {
    // ✅ 需要注入的依赖：使用 final
    private final UserService userService;
    private final OrderService orderService;

    // ✅ 常量：使用 static final
    private static final Logger log = LoggerFactory.getLogger(AdminService.class);
    private static final int MAX_RETRY = 3;

    // ❌ 避免可变实例变量
    // private List<User> cache = new ArrayList<>();

    // ✅ 如果必须有状态，使用线程安全容器
    private final ConcurrentHashMap<Long, User> cache = new ConcurrentHashMap<>();

    // ✅ 业务逻辑使用局部变量
    public void processOrder(Long orderId) {
        Order order = orderService.findById(orderId);  // 局部变量，线程安全
    }
}
```

### 8.2 Entity / DTO 层

```java
@Data                    // 生成 getter/setter/toString/equals/hashCode
@NoArgsConstructor      // 无参构造（框架需要）
@AllArgsConstructor     // 全参构造（可选）
public class User {
    private Long id;
    private String username;
    private String password;
}
```

> `@Data` 不会生成有参构造函数，如果需要全参构造必须额外加 `@AllArgsConstructor`。

### 8.3 核心原则速查

| 原则 | 说明 |
|------|------|
| 依赖注入用 `@RequiredArgsConstructor` + `final` | 编译时检查、线程安全、减少样板代码 |
| 避免字段注入 `@Autowired` | 依赖隐藏、无法用 `final`、不利于测试 |
| `final` 是注入的控制开关 | 只有 `final` 字段才会被 Lombok 生成到构造函数 |
| 单例 Bean 保持无状态 | 不使用可变实例变量，保证高并发线程安全 |
| 方法内使用局部变量 | 局部变量在栈内存中，线程隔离，天然安全 |
