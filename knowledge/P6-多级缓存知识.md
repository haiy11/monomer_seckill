# P6 多级缓存知识笔记（Caffeine → Redis → DB）

> 目标：秒杀场景下，热点商品信息（名称/价格/时间/状态）是读多写少、QPS 最高的数据。把这类数据放进「本地缓存 + 分布式缓存」两级缓存，把 DB 扛的读压力降到最低，从而降低响应时间、提高吞吐。

---

## 一、为什么要多级缓存

一次「读」的不同存储介质延迟量级（数量级概念，用于面试表达）：

| 层级 | 介质 | 延迟量级 | 说明 |
|------|------|----------|------|
| L1 | 本地缓存（JVM 内存，Caffeine） | **亚毫秒 ~ 1ms** | 进程内，无网络开销，但各实例独立、容量受内存限制 |
| L2 | 分布式缓存（Redis） | **1 ~ 5ms** | 跨实例共享，走网络；多实例数据一致 |
| L3 | 数据库（MySQL） | **几 ms ~ 几十 ms** | 磁盘 I/O + 连接 + SQL，最慢，且是系统最宝贵的资源 |

思路：**把最热的读请求挡在离用户最近的那一层**。绝大多数请求命中 L1（本地），少数穿透到 L2（Redis），极少数回源 L3（DB）。

> 为什么不能只用 Redis、不用本地缓存？Redis 是「分布式共享」的（多实例一致），但每次访问都要走网络、有序列化开销；本地缓存毫秒级甚至亚毫秒级，但多实例各自独立、需要额外解决一致性。所以「本地（快）+ 分布式（共享）」组合是经典做法。

## 二、本项目架构：读路径与写路径

本阶段把多级缓存抽成 `common-service` 里的通用组件 `MultiLevelCache<K, V>`，两个服务分别接入：

| 服务 | 缓存对象 | 缓存名 | Redis key | 说明 |
|------|----------|--------|-----------|------|
| seckill-service | `SeckillGoods`（秒杀商品） | `seckill-goods` | `seckill:goods:{id}` | **P6 核心**：热点秒杀商品详情/下单校验 |
| goods-order-service | `Goods`（正常商品） | `goods` | `goods:cache:{id}` | 复用同一组件，展示通用性 |

### 读路径（`MultiLevelCache.get(key)`）

```
L1 Caffeine 命中？ ──是──▶ 返回
        │否
L2 Redis 命中？  ──是──▶ 回填 L1，返回
        │否
L3 DB 查询       ──有值──▶ 写 L2（带 TTL）+ 写 L1，返回
                 └─空值──▶ 写 L2 空值占位（短 TTL），返回 null
```

要点：
- **逐级回填**：命中 L2 后顺手写进 L1，下次直接命中本地。
- **空值占位**：DB 查不到时，在 Redis 写一个 `__NULL__` 占位（短 TTL 60s），防止「查不存在的 id」反复穿透到 DB（缓存穿透）。
- 本地缓存**不缓存空值**（Caffeine 的 `Cache` 不允许 value 为 null），穿透保护由 Redis 空值占位兜底，足够。

### 写路径（Cache-Aside 旁路缓存：更新 DB 后删除缓存）

```
更新 DB  ──▶ 删 L1（本地） ──▶ 删 L2（Redis） ──▶ Redis Pub/Sub 广播 ──▶ 其它实例删各自 L1
```

要点：
- 采用**删除缓存**而非「刷新缓存」：删除是惰性的（下次读时回源重建），避免「更新后立刻刷新」在高并发下可能把旧值又写回去的竞态。
- **为什么还要广播？** L1 是各实例进程内的，删除只删了「当前这个实例」的本地缓存；其它实例的本地缓存还躺着旧值。通过 Redis Pub/Sub 把「删了哪个 key」广播出去，所有实例收到后同步删掉各自的 L1，最终一致。
- **事务提交后再删**（goods-order-service 的库存变化）：扣库存等操作在 `@Transactional` 事务内，若在提交前删缓存，其它请求可能回源读到「未提交的旧数据」并重新写回缓存，造成脏缓存。用 `TransactionSynchronization.afterCommit` 把删除推迟到提交后执行（`OrderService.evictGoodsCacheAfterCommit`）。

## 三、缓存三大经典问题（面试必考）

| 问题 | 是什么 | 本项目怎么应对 |
|------|--------|----------------|
| **缓存穿透** | 查询一个根本不存在的数据，每次都打到 DB | Redis 写 `__NULL__` 空值占位（短 TTL 60s）；本地缓存不缓存空值 |
| **缓存击穿** | 某个**热点 key** 过期瞬间，大量并发同时回源 DB | 本阶段**简化处理**：L1 用 Caffeine，未做「互斥锁/单飞」；真实项目可用「互斥锁 / 逻辑过期 / Caffeine 的 `get(key, loader)` 单飞」 |
| **缓存雪崩** | 大量 key 同时过期，或缓存整体宕机，流量全部打到 DB | TTL 分层（商品 30min、空值 60s、本地 5min）；本地缓存兜底；Sentinel 限流熔断（P5）继续兜底 |

> 面试表述：穿透靠「空值缓存 + 布隆过滤器」、击穿靠「互斥锁 / 永不过期 + 逻辑过期」、雪崩靠「过期时间加随机 + 多级缓存 + 限流」。

## 四、多级缓存一致性（本阶段重点）

本地缓存与分布式缓存并存，带来「多实例一致性」难题。核心策略：

1. **Cache-Aside**：读时回源写缓存，写时「先更新 DB、后删缓存」。
2. **失效广播**：删除 L2 后通过 Redis Pub/Sub 广播，各实例删自己 L1（`CacheEvictListener` + `MultiLevelCacheRegistry`）。
3. **本地短 TTL 兜底**：即使广播丢失（Redis 异常等），本地缓存 5 分钟自动过期，一致性最多滞后 5 分钟，不会永久脏。

> 更严格的一致性（延迟双删、订阅 binlog 如 Canal、分布式锁）属于进阶，本学习项目用「删除 + 广播 + 短 TTL」已经覆盖了核心思想。

## 五、关键代码结构

`common-service` 新增包 `com.example.seckill.common.cache`（纯基础设施，不含业务）：

| 类 | 职责 |
|----|------|
| `MultiLevelCache<K, V>` | 通用多级缓存：L1/L2/L3 读、逐级回填、空值占位、删除 + 广播。Builder 构建 |
| `MultiLevelCacheRegistry` | 维护「广播通道 → 缓存实例」，供订阅端定位缓存并删 L1 |
| `CacheEvictListener` | 订阅 Redis Pub/Sub `cache:evict:*`，转发给 registry |
| `MultiLevelCacheConfig` | 注册 `RedisMessageListenerContainer`，模式订阅 `cache:evict:*` |
| `CacheConstants` | 广播通道前缀、空值占位符、默认 TTL |

各服务在自己的 `CacheConfig` 里用 `MultiLevelCache.builder()` 组装出具体 Bean（指定 key 前缀、DB 加载函数、TTL 等）。

> 注意：两个服务的启动类 `@SpringBootApplication(scanBasePackages = ...)` 是**显式列举** common 包的，新增 `common.cache` 后必须把 `com.example.seckill.common.cache` 加进 `scanBasePackages`，否则这些组件不会被扫描到。

## 六、TTL 与 key 设计

| 项 | 值 | 理由 |
|----|----|------|
| 商品信息 Redis TTL | 1800s（30min） | 商品基础信息变化少，缓存久一点收益大 |
| 空值占位 TTL | 60s | 短一点，避免「新建商品后长时间返回不存在」 |
| 本地缓存 TTL | 300s（5min） | 广播失效之外的兜底，5 分钟上界保证最终一致 |
| 本地缓存容量 | 1000 条 | Caffeine `maximumSize`，防止内存被打爆 |

秒杀商品 Redis key 复用 P2 预留的 `seckill:goods:{id}`（与既有 `SeckillConstants.GOODS_KEY_PREFIX` 一致），因此历史缓存数据无需迁移。

## 七、一个值得想清楚的取舍：库存不要放进「商品信息」缓存

秒杀商品的 `seckillStock` 字段存在于 `seckill_goods` 表，但**实时剩余库存的权威来源是 Redis 预扣库存**（`seckill:stock:{id}`，P2 的 Lua 扣减）。

因此缓存的 `SeckillGoods` 实体里的 `seckillStock` 是一个「快照」，可能滞后于实时剩余库存。正确做法是**数据分层**：

- 「商品基础信息」（名称/价格/时间/状态）→ 多级缓存，变化少、可长缓存；
- 「实时库存」→ 单独用 Redis 维护（P2 已做），展示层需要实时库存时读 Redis，而不是读商品缓存。

> 面试加分点：主动指出「高频变化的数据（库存）和低频变化的数据（商品信息）要分开缓存，避免库存每次扣减都去失效商品缓存」。

---

## 八、与前面阶段的关系

- **P2 Redis 预扣库存**：库存走 Redis（Lua 原子扣减），与「商品信息」缓存是两套 key、两个用途，互不干扰。
- **P5 Sentinel**：缓存挡掉大部分读压力后，DB/Redis 更稳；万一缓存层异常（雪崩），Sentinel 限流熔断继续兜底，避免拖垮 DB。
- **P7 配置中心**：可以把 `MultiLevelCache` 的 TTL、Caffeine 容量等做成配置项，后续迁移到 Nacos Config 动态刷新。

## 九、面试话术模板

> 「针对秒杀商品详情这种热点读，我做了两级缓存：进程内用 Caffeine（亚毫秒级、容量上限 + 短 TTL），分布式用 Redis（多实例共享、空值占位防穿透）。读走 Caffeine → Redis → DB 逐级回填；写走 Cache-Aside——先更新 DB 再删缓存，并且因为本地缓存是各实例独立的，我用 Redis Pub/Sub 广播失效，让所有实例同步删自己的本地缓存，再用短 TTL 兜底，保证最终一致。这样把 DB 的读压力降了 1~2 个数量级，响应时间从毫秒级降到亚毫秒级。」
