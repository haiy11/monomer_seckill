# P6 多级缓存知识笔记（Caffeine → Redis → DB）

> 目标：秒杀场景下，热点商品信息（名称/价格/时间/状态）是读多写少、QPS 最高的数据。把这类数据放进「本地缓存 + 分布式缓存」两级缓存，把 DB 扛的读压力降到最低，从而降低响应时间、提高吞吐。

---

## 一、为什么要多级缓存

一次「读」的不同存储介质延迟量级（数量级概念，用于面试表达）：

| 层级 | 介质 | 延迟量级 | 说明 |
|------|------|----------|------|
| L1 | 本地缓存（JVM 内存，Caffeine） | **亚毫秒 ~ 1ms** | 进程内，无网络开销，但各实例独立、容量受内存限制 |
| L2 | 分布式缓存（Redis） | **1 ~ 5ms** | 跨实例共享，走网络；多实例数据一致 |
| L3 | 数据库（MySQL） | **几 ms ~ 几十 ms** | 磁盘 I/O + 连接 + SQL，最慢，且是系统最宝贵的资源 |

思路：**把最热的读请求挡在离用户最近的那一层**。绝大多数请求命中 L1（本地），少数穿透到 L2（Redis），极少数回源 L3（DB）。

> 为什么不能只用 Redis、不用本地缓存？Redis 是「分布式共享」的（多实例一致），但每次访问都要走网络、有序列化开销；本地缓存毫秒级甚至亚毫秒级，但多实例各自独立、需要额外解决一致性。所以「本地（快）+ 分布式（共享）」组合是经典做法。

## 二、架构总览：通用组件 + 两个服务接入

本阶段把多级缓存抽成 `common-service` 里的通用组件 `MultiLevelCache<K, V>`，两个服务分别接入：

| 服务 | 缓存对象 | 缓存名 | Redis key | 说明 |
|------|----------|--------|-----------|------|
| seckill-service | `SeckillGoods`（秒杀商品） | `seckill-goods` | `seckill:goods:{id}` | **P6 核心**：热点秒杀商品详情/下单校验 |
| goods-order-service | `Goods`（正常商品） | `goods` | `goods:cache:{id}` | 复用同一组件，展示通用性 |

### 一个服务只能缓存一类数据吗？—— 能，想缓存几类就几类

`MultiLevelCache` 是**普通类**（没有 `@Component`/`@Service`，**不交给 Spring 管理**），它的实例化权在你自己写的 `CacheConfig` 里。`CacheConfig` 里可以写**多个 `@Bean` 方法**，每个 `@Bean` 返回一个不同用途的 `MultiLevelCache`。

只要每个实例满足三点，就能并存：

| 条件 | 作用 |
|------|------|
| `name` 唯一 | 决定广播通道 `cache:evict:{name}` 唯一，`MultiLevelCacheRegistry` 靠它区分 |
| `redisKeyBuilder` 前缀不同 | 避免 Redis key 冲突 |
| `valueType` 对应各自实体 | JSON 反序列化目标类型 |

例如在秒杀服务里再加「秒杀订单缓存」，只需在 `CacheConfig` 里再加一个 `@Bean`：

```java
@Bean
public MultiLevelCache<Long, SeckillGoods> seckillGoodsCache(...) { ... }  // 第一类：商品
@Bean
public MultiLevelCache<Long, SeckillOrder> seckillOrderCache(...) { ... }  // 第二类：订单
```

底层支撑：`MultiLevelCacheRegistry` 用 `ConcurrentHashMap<channel, cache>`，`channel = "cache:evict:" + name`。`name` 不重复就能注册 N 个，收到消息时按 channel 精确路由到对应的那个缓存实例。

> 所以「一个服务只能缓存一类」只是**本次 P6 每个服务恰好只接了一类**，不是框架限制。

## 三、读路径（`MultiLevelCache.get(key)`）

```
L1 Caffeine 命中？ ──是──▶ 返回
        │否
L2 Redis 命中？  ──是──▶ 回填 L1，返回
        │否
L3 DB 查询       ──有值──▶ 写 L2（带 TTL）+ 写 L1，返回
                 └─空值──▶ 写 L2 空值占位（短 TTL），返回 null
```

要点：
- **逐级回填**：命中 L2 后顺手写进 L1，下次直接命中本地。
- **空值占位**：DB 查不到时，在 Redis 写一个 `__NULL__` 占位（短 TTL 60s），防止「查不存在的 id」反复穿透到 DB（缓存穿透）。
- 本地缓存**不缓存空值**（Caffeine 的 `Cache` 不允许 value 为 null），穿透保护由 Redis 空值占位兜底，足够。

## 四、写路径与缓存一致性（本阶段重点）

### 4.1 Cache-Aside（旁路缓存）：更新 DB 后删除缓存

```
更新 DB  ──▶ 删 L1（本地） ──▶ 删 L2（Redis） ──▶ Redis Pub/Sub 广播 ──▶ 其它实例删各自 L1
```

核心策略三条：

1. **Cache-Aside**：读时回源写缓存，写时「先更新 DB、后删缓存」。
2. **失效广播**：删除 L2 后通过 Redis Pub/Sub 广播，各实例删自己 L1（`CacheEvictListener` + `MultiLevelCacheRegistry`）。
3. **本地短 TTL 兜底**：即使广播丢失（Redis 异常等），本地缓存 5 分钟自动过期，一致性最多滞后 5 分钟，不会永久脏。

采用**删除缓存**而非「刷新缓存」：删除是惰性的（下次读时回源重建），避免「更新后立刻刷新」在高并发下可能把旧值又写回去的竞态。

### 4.2 删除顺序与竞态分析（先删本地 → 删 Redis → 广播，安全吗？）

`evict(key)` 的实现顺序：

```java
local.invalidate(redisKey);           // ① 删本地 L1
redis.delete(redisKey);               // ② 删分布式 L2
redis.publish(evictChannel, redisKey); // ③ 广播其它实例删 L1
```

把「写线程 W 更新商品、读线程 R 读同一商品」的时序摊开：

```
W: local.invalidate(key)        // ① 删本地
   （窗口 A）R: 本地没命中 → Redis 读到【旧值】→ 回填本地旧值
W: redis.delete(key)            // ② 删 Redis
   （窗口 B）R': 本地没命中 → Redis 没命中 → 回源 DB → 回填本地
W: redis.publish(channel, key)  // ③ 广播
   （所有实例，含 W 自己）收到消息 → evictLocalByKey(key) → 再删一次本地
```

逐段结论：

- **窗口 A 里 R 回填的旧值**：会被第 ③ 步广播删掉。因为**发布者自己也订阅了同一通道**（同实例既有订阅连接 container、又有发布连接 `StringRedisTemplate`，Redis 会把消息推给所有匹配的订阅连接，不区分是否同一进程），广播会回到本实例，`evictLocalByKey` 再 `local.invalidate` 一次，把刚回填的旧值清掉。→ **能无效掉。**
- **窗口 B 里 R' 回填的值**：
  - 若是**非事务**场景（秒杀商品：`updateById` 后 MyBatis-Plus 自动提交，DB 已是新值），回源读到新值，回填没有危害；
  - 若是**事务**场景（正常商品扣库存还在 `@Transactional` 里没提交），回源可能读到未提交旧值——这正是 `OrderService` 用 `TransactionSynchronization.afterCommit` 把「删缓存 + 广播」整体推迟到**事务提交后**的原因：保证「提交」一定发生在「删缓存/广播」之前，消灭「删完又读到未提交旧值」的窗口。

一句话总结：

> 对「秒杀商品」这类非事务单条 update，`先删本地 → 删 Redis → 广播` 已经足够，广播会把窗口内误回填的本地旧值再清一遍；对「订单扣库存」这类多语句事务，把整套删除推迟到 `afterCommit`，避免读到未提交旧值。二者共同保证**最终一致**，剩余极短脏读窗口由本地 5 分钟 TTL 兜底，不会永久脏。

> 更严格的一致性（延迟双删、订阅 binlog 如 Canal、分布式锁）属于进阶，本学习项目用「删除 + 广播 + 短 TTL」已覆盖核心思想。

## 五、缓存三大经典问题（面试必考）

| 问题 | 是什么 | 本项目怎么应对 |
|------|--------|----------------|
| **缓存穿透** | 查询一个根本不存在的数据，每次都打到 DB | Redis 写 `__NULL__` 空值占位（短 TTL 60s）；本地缓存不缓存空值 |
| **缓存击穿** | 某个**热点 key** 过期瞬间，大量并发同时回源 DB | 本阶段**简化处理**：L1 用 Caffeine，未做「互斥锁/单飞」；真实项目可用「互斥锁 / 逻辑过期 / Caffeine 的 `get(key, loader)` 单飞」 |
| **缓存雪崩** | 大量 key 同时过期，或缓存整体宕机，流量全部打到 DB | TTL 分层（商品 30min、空值 60s、本地 5min）；本地缓存兜底；Sentinel 限流熔断（P5）继续兜底 |

> 面试表述：穿透靠「空值缓存 + 布隆过滤器」、击穿靠「互斥锁 / 永不过期 + 逻辑过期」、雪崩靠「过期时间加随机 + 多级缓存 + 限流」。

## 六、广播原理：Redis Pub/Sub 失效通知

### 6.1 是推送，不是查询

「客户端读本地缓存时先查 Redis 看有没有失效」是**错的**——广播是 **Redis 主动推送**，读路径零额外开销。流程：

1. **订阅**：每个服务实例启动时，`RedisMessageListenerContainer` 向 Redis 发 `PSUBSCRIBE cache:evict:*`，Redis 服务器**记住**「这个连接订阅了该模式」。
2. **发布**：写方执行 `redis.publish("cache:evict:seckill-goods", "seckill:goods:1")`，把消息交给 Redis 服务器。
3. **推送**：Redis 服务器**主动**把消息沿网络连接推给所有匹配的订阅连接，订阅端的 `MessageListener.onMessage()` 被回调。
4. **删本地**：回调里解析出 key，删本进程内 Caffeine 缓存。

所以是「Redis 通知你，你被动收」，不是「轮询/查询」。

### 6.2 三个广播类各自的作用

| 类 | 职责 | 类比 |
|----|------|------|
| `MultiLevelCacheConfig` | `@Configuration`，创建 `RedisMessageListenerContainer` bean，订阅模式 `cache:evict:*`，并把 `CacheEvictListener` 注册为回调 | 「架设电话线 + 指定谁接电话」 |
| `CacheEvictListener` | `implements MessageListener`，真正的回调：`onMessage()` 解析出 `channel` 和 `body`（被删的 redis key），转交 registry | 「接电话，报出频道与 key」 |
| `MultiLevelCacheRegistry` | `@Component`，维护 `channel → MultiLevelCache实例` 映射，是路由层：按 channel 找到对应缓存实例，调 `evictLocalByKey()` | 「查电话簿，找到实例执行」 |

### 6.3 一次失效广播的完整链路

```
写方某个实例:
  MultiLevelCache.evict(key)
     → local.invalidate + redis.delete + redis.publish("cache:evict:seckill-goods", "seckill:goods:1")

                        │ (交给 Redis 服务器)
                        ▼
读方所有实例(含写方自己):
  RedisMessageListenerContainer 收到推送
     → 回调 CacheEvictListener.onMessage(message, pattern)
     → 解析 channel="cache:evict:seckill-goods", body="seckill:goods:1"
     → MultiLevelCacheRegistry.evict(channel, body)
     → 查表找到 name="seckill-goods" 的 MultiLevelCache 实例
     → 该实例.evictLocalByKey("seckill:goods:1")
     → local.invalidate("seckill:goods:1")   // 删本进程本地缓存
```

为什么需要 Registry 而不是让 Listener 直接删？因为一个服务里可能同时存在多个缓存（多个 channel），消息进来时得知道「这条消息属于哪个缓存实例」，Registry 就是那张映射表。

### 6.4 `MessageListener` 的其它实现类都能监听吗？

- 本项目里 `implements MessageListener` 的**只有 `CacheEvictListener` 一个**。
- 更重要的原理：**「实现 `MessageListener` 接口」≠「会自动监听」**。它只是个回调接口，必须显式 `container.addMessageListener(listener, new PatternTopic("cache:evict:*"))` 注册进某个 `RedisMessageListenerContainer` 才会收到消息。
- 在 IDE 里看到的其它实现类，大概率是 **Spring 框架内部**的（Lettuce/Jedis 连接工厂内部、`MessageListenerAdapter` 等），它们不是业务监听器，也不会被注册到我们的 container，与我们互不干扰。
- Spring Boot 3.x 有实验性的 `@RedisMessageListener` 注解可自动注册，本项目没用，用的是显式 `RedisMessageListenerContainer` + `addMessageListener`。

## 七、TTL 与 key 设计

| 项 | 值 | 理由 |
|----|----|------|
| 商品信息 Redis TTL | 1800s（30min） | 商品基础信息变化少，缓存久一点收益大 |
| 空值占位 TTL | 60s | 短一点，避免「新建商品后长时间返回不存在」 |
| 本地缓存 TTL | 300s（5min） | 广播失效之外的兜底，5 分钟上界保证最终一致 |
| 本地缓存容量 | 1000 条 | Caffeine `maximumSize`，防止内存被打爆 |

秒杀商品 Redis key 复用 P2 预留的 `seckill:goods:{id}`（与既有 `SeckillConstants.GOODS_KEY_PREFIX` 一致），因此历史缓存数据无需迁移。

## 八、一个值得想清楚的取舍：库存不要放进「商品信息」缓存

秒杀商品的 `seckillStock` 字段存在于 `seckill_goods` 表，但**实时剩余库存的权威来源是 Redis 预扣库存**（`seckill:stock:{id}`，P2 的 Lua 扣减）。

因此缓存的 `SeckillGoods` 实体里的 `seckillStock` 是一个「快照」，可能滞后于实时剩余库存。正确做法是**数据分层**：

- 「商品基础信息」（名称/价格/时间/状态）→ 多级缓存，变化少、可长缓存；
- 「实时库存」→ 单独用 Redis 维护（P2 已做），展示层需要实时库存时读 Redis，而不是读商品缓存。

> 面试加分点：主动指出「高频变化的数据（库存）和低频变化的数据（商品信息）要分开缓存，避免库存每次扣减都去失效商品缓存」。

## 十、与前面阶段的关系

- **P2 Redis 预扣库存**：库存走 Redis（Lua 原子扣减），与「商品信息」缓存是两套 key、两个用途，互不干扰。
- **P5 Sentinel**：缓存挡掉大部分读压力后，DB/Redis 更稳；万一缓存层异常（雪崩），Sentinel 限流熔断继续兜底，避免拖垮 DB。
- **P7 配置中心**：可以把 `MultiLevelCache` 的 TTL、Caffeine 容量等做成配置项，后续迁移到 Nacos Config 动态刷新。

## 十一、面试话术模板

> 「针对秒杀商品详情这种热点读，我做了两级缓存：进程内用 Caffeine（亚毫秒级、容量上限 + 短 TTL），分布式用 Redis（多实例共享、空值占位防穿透）。读走 Caffeine → Redis → DB 逐级回填；写走 Cache-Aside——先更新 DB 再删缓存，并且因为本地缓存是各实例独立的，我用 Redis Pub/Sub 广播失效，让所有实例同步删自己的本地缓存，再用短 TTL 兜底，保证最终一致。这样把 DB 的读压力降了 1~2 个数量级，响应时间从毫秒级降到亚毫秒级。」
